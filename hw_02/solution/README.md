# ДЗ 2. Проектирование взаимодействия сервисов — сервис бронирования

## Выбранная система

**Сервис бронирования отелей (аналог Booking.com).**

Основные сценарии: поиск объекта размещения, проверка доступности, создание бронирования, временная фиксация номера, оплата, подтверждение и отмена.

Ключевые сложности системы:

- нельзя допускать двойное бронирование одного номера;
- оплата выполняется через внешний платёжный провайдер;
- отмена может требовать возврата денег и освобождения инвентаря;
- поиск имеет намного большую нагрузку, чем операции записи;
- часть операций должна выполняться асинхронно.

## 1. Декомпозиция

В системе выделено **7 сервисов**.

| № | Сервис | Ответственность |
|---|---|---|
| 1 | **API Gateway** | Единая внешняя точка входа, аутентификация JWT, rate limit, маршрутизация REST/GraphQL во внутренние API |
| 2 | **Catalog Service** | Объекты размещения, типы номеров, тарифы, правила бронирования и описание объектов |
| 3 | **Search Service** | Поиск по географии, датам и фильтрам; отдельная read-модель для быстрого чтения |
| 4 | **Inventory Service** | Фактическая доступность номеров, soft-hold, подтверждение и освобождение номеров |
| 5 | **Booking Service** | Брони как бизнес-агрегаты, их статусы и оркестрация процесса бронирования |
| 6 | **Payment Service** | Payment Intent, подтверждение оплаты, возвраты, идемпотентность и обработка webhook от провайдера. Имеет внешние зависимости. |
| 7 | **Notification Service** | Отправка email/SMS после событий бронирования и оплаты |

**Search** отделён от write-path. Он может работать с eventually consistent read-моделью и масштабироваться независимо от операций бронирования.
**API Gateway** использует внешний Identity Provider (Keycloak/Auth0)

## 2. Протоколы взаимодействия

В системе используется **комбинация протоколов**, потому что разные сценарии имеют разные требования.

| Взаимодействие | Протокол/Фреймворк | Обоснование |
|---|---|---|
| Клиент → API Gateway: бронирование, отмена, оплата | **REST/HTTPS** | Универсальность, кеш, отладка, browser |
| Клиент → API Gateway: поиск | **GraphQL/HTTPS** | Клиенту нужен разный набор полей для списка, карты и карточки объекта |
| Gateway → внутренние сервисы | **gRPC** | Типизация, скорость, контракты, streaming gRP |
| Booking → Inventory | **gRPC** | Hold/Confirm/Release требуют непосредственного ответа |
| Booking → Payment | **gRPC** | Создание Payment Intent и возврат должны иметь явный результат |
| Сервисы → Kafka | **Events** | Асинхронная доставка фактов, fan-out и буферизация пиков |
| Payment Provider → Payment | **REST webhook/callback** | Внешний провайдер сообщает результат операции асинхронно |

## 3. Схема взаимодействия

Полная схема находится в:

`diagrams/booking-interaction.puml`

На схеме указаны:

- внешние акторы;
- 7 сервисов;
- Kafka;
- внешний платёжный провайдер;
- направления взаимодействия;
- протокол на каждом основном ребре;
- синхронный и асинхронный контуры.

Основной поток:

`Клиент → Gateway → Booking → Inventory (Hold) → Payment (CreateIntent)`

После оплаты:

`Payment Provider → Webhook → Payment → Kafka → Booking → Inventory (Confirm)`

При отмене:

`Клиент → Gateway → Booking → Inventory (Release)`

и, если деньги уже списаны:

`Booking → Payment (Refund)`

## 5. Асинхронность

Асинхронное взаимодействие используется там, где вызывающему сервису не нужен немедленный ответ.

| Сценарий | Модель | Причина |
|---|---|---|
| Поиск | Синхронно | Пользователь ожидает результаты сразу |
| Бронь номера | Синхронно | Без подтверждённой брони нельзя продолжать оплату |
| Создание платежной сессии | Синхронно | Клиенту нужен `paymentIntentId` и состояние оплаты |
| Результат оплаты от провайдера | Асинхронно | Провайдер сообщает факт операции через webhook/callback |
| Обновление Search read-model | Асинхронно | Поиск не должен блокировать запись |
| Отправка email/SMS | Асинхронно | Уведомление не должно задерживать бронирование |
| Истечение TTL брони номера | Асинхронно | Бронь может истечь без действия пользователя |

| Topic | Событие | Продюсер | Консьюмеры | Назначение |

## 6. Паттерны

### 6.1 Saga с оркестрацией

Оркестратором выступает **Booking Service**.

Основной сценарий:

1. Создать бронь в статусе `PENDING`.
2. Выполнить `Inventory.Hold` и получить holdId и expiresAt. Удержание действует ограниченное время, например 15 минут.
3. Выполнить `Payment.CreateIntent`.
4. Перевести бронь в `HELD`. Пользователь подтверждает платёж, при необходимости проходит 3-D Secure.
5. После `payment.captured` выполнить `Inventory.Confirm`.
6. Если Inventory успешно подтвердил удержание, перевести бронирование в статус CONFIRMED и опубликовать booking.confirmed.

Компенсации:

- Не удалось создать Payment Intent -> `Inventory.Release`
- Получено событие payment.failed до списания -> Освободить hold, если он ещё активен
- не удалось создать оплату → `Inventory.Release`;
- платёж не прошёл → `Inventory.Release`;
- отмена подтверждённой брони → `Payment.Refund` + `Inventory.Release`.
- Платёж успешно списан, но Inventory.Confirm вернул HOLD_EXPIRED -> Запустить возврат через Payment.Refund
- Возврат не удалось завершить -> Оставить бронь в REFUND_PENDING, повторить обработку и запустить сверку с Payment

Оплата после истечения hold:

Подтверждение оплаты может прийти уже после окончания 3-D Secure или длительной обработки платежа.

- Inventory Service освобождает просроченный hold и публикует inventory.released.
- Booking Service переводит бронь в EXPIRED, если она ещё не подтверждена.
- Если позднее приходит payment.captured, Booking Service не игнорирует событие, даже если статус брони уже EXPIRED.
- Booking вызывает Inventory.Confirm(holdId). Если удержание уже истекло или освобождено, Inventory возвращает ошибку HOLD_EXPIRED либо соответствующую ошибку недоступности hold.
- Booking переводит бронь в REFUND_PENDING и вызывает Payment.Refund с идемпотентным ключом, например refund:{bookingId}.
- После подтверждённого возврата Payment Service публикует payment.refunded. Booking переводит бронь в FAILED и публикует booking.failed.
- Если возврат не завершился, статус остаётся REFUND_PENDING. Система повторяет обработку по политике повторов и выполняет сверку с платёжным провайдером.
- Статус FAILED в этой ветке означает, что бронь не состоялась, а возврат успешно завершён. До подтверждения возврата используется REFUND_PENDING.

Saga используется вместо распределённой транзакции, потому что сервисы имеют отдельные базы данных и внешние зависимости.

Маршрутизация, rate limiting, аутентификация, метрики, логирование, кэширование.

### 6.3 CQRS для поиска

Search Service использует отдельную read-модель.

Изменения приходят через Kafka, а чтение выполняется из поискового индекса.

Преимущество:

- поиск масштабируется независимо;
- сложные фильтры не нагружают транзакционные БД;
- задержка обновления допускается, потому что окончательная доступность проверяется в Inventory.

### 6.4 Idempotency Key

Для создания брони, оплаты, refund и отмены используется `Idempotency-Key`.

Это защищает систему от повторной отправки запроса при сетевых сбоях.

Например, если клиент повторил `POST /v1/bookings` с тем же ключом, второй hold не создаётся.

Webhook также должен быть идемпотентным: повторное событие с тем же `eventId` не должно повторно проводить бизнес-операцию.

### 6.5 Transactional Outbox

Сервис сначала фиксирует изменение состояния и запись о событии в одной локальной транзакции БД.

После commit отдельный publisher отправляет событие в Kafka.

Это уменьшает риск ситуации, когда запись в БД прошла, а событие потерялось.
