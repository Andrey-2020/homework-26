# ДЗ 5. Отказоустойчивость, observability и тестирование — решение

**Система:** Booking.com — сервис бронирования отелей, продолжение ДЗ 2–4.

---

## Отказоустойчивость

### 1. RTO / RPO по сервисам

| Сервис | Приоритет | RPO: локально / региональный DR | RTO: локально / региональный DR | Обоснование |
|---|---|---|---|---|
| **Booking + `db`** | Tier 0 | ≤ 1 мин / ≤ 5 мин | ≤ 3 мин / ≤ 12 мин | Хранит статус брони и шаг Saga. Потеря подтверждённого перехода может оставить бронь несогласованной с Inventory/Payment. В DR нужна сверка с платёжным провайдером и повторная обработка событий. |
| **Inventory + `db`** | Tier 0 | ≤ 1 мин / ≤ 5 мин | ≤ 3 мин / ≤ 12 мин | Источник истины по слотам и hold. При потере последних изменений риск overbooking выше цены временного отказа в продажах. После регионального переключения продажи по затронутым датам блокируются до reconciliation. |
| **Payment + `db`** | Tier 0 | ≤ 1 мин / ≤ 5 мин | ≤ 3 мин / ≤ 12 мин | Хранит Payment Intent, ключи идемпотентности и журнал webhook. В региональном DR состояние сверяется с провайдером до повторного capture/refund, чтобы не допустить двойной операции. |
| **Kafka** | Tier 0 для событий Saga | ≈ 0 для ack-сообщений / ≤ 5 мин | ≤ 5 мин / ≤ 15 мин | Подтверждённые записи реплицируются внутри кластера по всем репликам. Межрегиональная репликация асинхронная, поэтому RPO при потере региона не равен нулю. |
| **Catalog + `db`** | Tier 1 | ≤ 1 мин / ≤ 15 мин | ≤ 10 мин / ≤ 45 мин | Потеря последних партнёрских изменений неприятна, но не должна приводить к продаже одного номера дважды. Каталог можно восстановить из резервной копии и журнала изменений. |
| **Search + OpenSearch** | Tier 1 | Источник данных не теряется; индекс воспроизводится из Catalog/Inventory/Kafka | ≤ 10 мин / ≤ 60 мин | Поисковый индекс — производная модель. При необходимости он пересоздаётся; до завершения индексации Search может отдавать кэшированные/частичные результаты или сообщать о временной недоступности поиска. |
| **API Gateway** | Tier 1 по доступности входа (stateless) | Не применимо, нет бизнес-данных | ≤ 3 мин / ≤ 10 мин | Stateless-инстансы разворачиваются из образа за балансировщиком. Нужны минимум два экземпляра в разных AZ и инфраструктура, описанная в IaC. |
| **Notification** | Tier 2 | Не применимо, состояние восстанавливается по Kafka | ≤ 10 мин / ≤ 30 мин | Задержка письма/SMS не должна блокировать бронирование. Consumer возобновляет обработку сохранённых событий после восстановления. |
| **Redis** | Tier 2 | Не применимо, кэш не является SoT | ≤ 5 мин / ≤ 15 мин | Потеря кэша увеличит нагрузку на OpenSearch/PostgreSQL, но не должна терять бронь или платёж. Кэш заполняется заново. |

### 2. Репликация критичных БД

Для БД сервисов `Booking`, `Inventory` и `Payment` используется отдельный PostgreSQL-кластер на каждый сервис:

1. **Основная зона:** Primary принимает записи.
2. **Вторая зона того же региона:** синхронная standby-реплика. Коммит считается подтверждённым после записи WAL на standby. При потере Primary контроллер выбирает актуальную реплику.
3. **DR-регион:** асинхронная реплика получает WAL независимо. Она не участвует в каждом коммите, чтобы межрегиональная задержка не увеличивала latency всех записей.
4. **Failover control plane:** оркестратор (например, Patroni-подобное решение) с кворумом DCS и fencing старого лидера. Старый Primary не должен продолжать принимать записи после promote — это защита от split-brain.
5. **Routing:** приложение подключается через стабильный writer endpoint/proxy, а не хранит адрес Primary. На пути Saga (`Hold/Confirm/Release`) чтение выполняется с Primary, чтобы не принять решение по отстающей реплике.
6. **Backup/PITR:** регулярные зашифрованные backup и WAL-архивирование в отдельном аккаунте/проекте. Репликация не защищает от логической ошибки или ошибочного `DELETE`, который синхронно разойдётся по репликам.

Для менее критичного Catalog допустима асинхронная реплика в основном регионе. OpenSearch не считается источником истины и восстанавливается из Catalog, Inventory и Kafka.

### 3. Паттерны отказоустойчивости

| Паттерн | Где применяем | Правило | Зачем / ограничения |
|---|---|---|---|
| **Timeout / deadline** | Gateway→Booking; Booking→Inventory/Payment; Payment→провайдер | Начальные бюджеты: Gateway→Booking 2 с; `Inventory.Hold/Confirm/Release` 500 мс; `Payment.CreateIntent` 1,5 с; сетевой вызов провайдера 3 с. Все значения проверяются нагрузочным тестом. | Не даём зависшему вызову занимать пул бесконечно. Время ожидания 3-D Secure не включаем в latency самого Payment API. |
| **Retry с backoff + jitter** | gRPC и сетевые вызовы; Kafka consumers | До 2 повторов только для временных ошибок (`UNAVAILABLE`, connection reset, безопасно обработанный timeout); паузы, например 100–300 мс с jitter. Повторные команды используют один idempotency key. | Не повторяем бизнес-отказы (`SOLD_OUT`, `PRICE_CHANGED`, `CANCEL_NOT_ALLOWED`). При неизвестном результате платежа сначала сверяем состояние по ключу/у провайдера, а не делаем слепой повтор списания. |
| **Idempotency** | Создание/отмена брони, Hold, capture/refund, webhook и consumer-ы | Стабильный ключ для каждой бизнес-операции. | At-least-once доставка и сетевые повторы не должны создавать второй hold, capture или refund. |
| **Circuit breaker** | Payment→платёжный провайдер; Search→OpenSearch | Открывать breaker, например, при >50% технических ошибок в окне 30 с при достаточном числе запросов; пробовать half-open после паузы 20 с. | При сбое провайдера быстро возвращаем `PROCESSING`/понятный временный ответ или ошибку. Для Inventory нет fail-open: при недоступности источника истины нельзя подтверждать бронь по предположению. Search может кратковременно отдать кэшированный результат с ограничением свежести. |
| **Bulkhead** | Booking: отдельные пулы/лимиты для Inventory и Payment; отдельные consumer groups Kafka | Не использовать общий неограниченный пул для разных зависимостей. Ограничивать параллельные вызовы к одному горячему `asset_id`. | Медленный провайдер не должен исчерпать ресурсы, необходимые для `Inventory.Hold`; всплеск запросов одного отеля не должен положить все бронирования. |
| **Backpressure / rate limit** | API Gateway, Inventory, Kafka consumers | Ограничивать всплески, возвращать `429` для превышения пользовательских квот, масштабировать consumer-ы по lag. | Контролируемый отказ лучше каскадного таймаута. Бизнес-отказ по остаткам (`SOLD_OUT`) отделяем от технической деградации. |

**Fallback:** при недоступности Search/OpenSearch допускается устаревшая поисковая выдача из кэша с ограничением по времени. При недоступности Inventory запрос создания брони завершается временной ошибкой (`503`), а не использует Search или Redis как источник доступности.

### 4. План DR

DR — это не только техническая схема, а операционный план: критерии объявления аварии, ответственные роли, порядок восстановления, коммуникации и регулярные учения.

### 4.1. Сценарии катастроф и критерии запуска

| Сценарий | Это DR? | Как реагируем |
|---|---|---|
| Падение одного процесса/инстанса приложения | Нет | Автоматическое удаление нездорового экземпляра из балансировщика и перераспределение трафика. |
| Потеря одной Availability Zone | Обычно нет | Локальный HA: failover PostgreSQL на синхронную реплику, перераспределение приложений и Kafka по оставшимся зонам. Incident Commander уведомляется, но регион не переключается автоматически без проверки. |
| Основной регион целиком недоступен | Да | Запускаем региональный DR и восстанавливаем сервисы в регионе B по tier-приоритету. |
| Ошибочное удаление/повреждение бизнес-данных | Отдельный сценарий восстановления данных | Репликация не помогает, так как ошибка копируется на реплики. Останавливаем опасные записи, используем PITR/backup и проверяем целостность перед возобновлением продаж. |
| Недоступен только платёжный провайдер | Нет, это инцидент зависимости | Открываем circuit breaker, не делаем слепых повторов capture/refund, сохраняем операции в ожидающем состоянии и сверяем их после восстановления провайдера. |

**Критерий объявления регионального DR:** регион A недоступен минимум 5 минут по проверкам как минимум из двух независимых точек мониторинга, а локальный failover внутри региона не восстановил критический путь. Единолично объявляет DR **Incident Commander (IC)** после короткой проверки статуса облачного региона и связи с on-call платформы. Не переключаем запись на регион B только по одному алерту: это может создать split-brain.

### 4.2. Выбор DR-стратегии по тирам

| Tier | Компоненты Booking.com | Стратегия | Целевой RTO после региональной аварии | Почему |
|---|---|---|---|---|
| **Tier 0** | Booking, Inventory, Payment, Kafka | **Warm Standby**: реплики данных и небольшой рабочий набор приложения в регионе B уже запущены; при аварии масштабируем до целевой мощности | ≤ 12–15 минут | Эти компоненты отвечают за подтверждение брони, доступность номеров и деньги. Разворачивать их с нуля слишком долго, а Active-Active добавляет риск конфликтующих записей и стоимость. |
| **Tier 1** | Catalog, Search, внешний Identity Provider integration, API Gateway | **Pilot Light** для приложения и данных; базовая сеть, доступы, образы и данные подготовлены заранее, рабочая мощность поднимается при аварии | ≤ 30–60 минут для полного восстановления; Gateway поднимается раньше для проверки маршрутизации | Каталог и поиск важны для UX, но Search можно пересобрать из Catalog/Inventory/Kafka. Gateway stateless и разворачивается из конфигов; его нужно поднять до открытия трафика, даже если его данные не критичны. |
| **Tier 2** | Notification, Redis-кэш | **Backup & Restore / redeploy** | ≤ 30 минут | Notification может временно отставать, а Redis не хранит источник истины. Можно восстановить компоненты после критического пути, затем обработать накопленные события и прогреть кэш. |


### 4.3. Роли и связь при инциденте

| Роль | Ответственность | Канал связи |
|---|---|---|
| **Incident Commander (IC)** | Объявляет/закрывает DR, назначает приоритеты, фиксирует время событий и принимает решение о переключении трафика | Дежурный канал инцидента + телефон/pager |
| **Site Reliability Engineering (SRE) on-call** | Проверяет регион, сеть, IAM, DNS, секреты, разворачивает приложение и переключает маршрутизацию | Pager + канал инцидента |
| **Database Administrator (DBA) / Data on-call** | Проверяет lag, fencing старых primary, promote реплик, backup/PITR и целостность данных | Pager + канал инцидента |
| **Booking / Inventory / Payment owners** | Проверяют Saga, остатки, идемпотентность, незавершённые платежи и возвраты; запускают reconciliation | Канал инцидента; отдельные треды сервисов |
| **Kafka / Search owner** | Переключает producers/consumers, проверяет lag/replay, при необходимости пересобирает Search index | Канал инцидента |
| **Communications / Support lead** | Публикует согласованные сообщения гостям и партнёрам, собирает обращения и не обещает неподтверждённый срок восстановления | Status page, support channel, партнёрская рассылка |


### 4.4. Runbook восстановления региона

Сначала нужно восстановить доступы и безопасное управление данными, затем критичные транзакционные компоненты, после них чтение и фоновые процессы.

| Шаг | Владелец | Действие | Проверка перед переходом дальше |
|---:|---|---|---|
| 1 | IC + SRE | Объявить DR после выполнения критериев 4.1; зафиксировать время начала, scope, ответственных; заморозить обычные релизы и миграции | Инцидент зарегистрирован, владельцы назначены, связь работает |
| 2 | SRE / Security | Подготовить регион B: IAM-права, сеть, security groups, DNS, сертификаты, KMS-доступ, secrets manager и доступ к backup | Сервисы могут безопасно получить секреты и подключиться к зависимостям; секреты не копируются вручную в чат/логи |
| 3 | DBA + SRE | старый регион: гарантированно запретить запись на старых Primary и остановить маршрутизацию write-запросов в регион A | Подтверждено, что прежние Primary не могут принимать новые записи; только после этого разрешён promote |
| 4 | DBA | Проверить последний WAL/checkpoint и lag; promote реплик БД сервисов `Booking`, `Inventory` и `Payment` в регионе B | Все три БД доступны на запись; зафиксирован фактический потенциальный RPO и источник времени последнего подтверждённого WAL |
| 5 | Kafka owner | Переключить producers/consumers на DR-кластер Kafka; возобновить чтение по timestamp/checkpoint и допустить безопасную повторную обработку | Нет критических ошибок схемы/consumer; повторы не вызывают повторный capture/refund благодаря идемпотентности |
| 6 | Booking / Payment owners | Выполнить reconciliation Payment с провайдером по `payment_intent_id`, `provider_event_id` и idempotency key; неопределённые capture/refund не повторять вслепую | Каждая неизвестная операция классифицирована как выполненная, не выполненная или оставленная на ручной разбор |
| 7 | Inventory owner | Пересчитать доступность по затронутым объектам/датам; сверить `holds`, `CONFIRMED`, `RELEASED` и события в пределах окна возможной потери асинхронной репликации | Если состояние слота не доказано, новые Hold для соответствующего `asset_id`&дат временно запрещены; overbooking не допускается |
| 8 | SRE + owners | Масштабировать и проверить Tier 0 Booking, Inventory, Payment; поднять Gateway и компоненты Tier 1, затем Notification и Redis | Health checks зелёные, DB pool и Kafka доступны, API направляет записи только на новые Primary |
| 9 | Search/Kafka owner | Проверить полноту проекции Search; при повреждении/отставании индекса пересобрать его из Catalog, Inventory и Kafka; Notification догоняет backlog | Свежесть Search в пределах цели либо включён явно обозначенный деградированный режим |
| 10 | IC + владельцы сервисов | Выполнить synthetic test: поиск → Hold → тестовая оплата → Confirm; затем отмена и асинхронный refund на тестовом аккаунте. Только после успеха открыть основной трафик | Нет двойных списаний, бронь не подтверждается без Inventory Confirm, возврат переходит из `REFUND_PENDING` в конечное состояние |
| 11 | IC + Communications | Переключить DNS/GSLB на регион B, постепенно увеличить долю трафика и опубликовать статус для гостей/партнёров | Ошибки и latency стабильны на canary и при постепенном увеличении трафика |
| 12 | IC + все владельцы | Закрыть DR, записать фактические RTO/RPO, потерянные/повторно обработанные события, решения по спорным операциям и действия для устранения причин | Назначены владельцы и сроки postmortem-действий; восстановление подтверждено не только health check, но и бизнес-сценариями |

### 4.5. Коммуникации

| Кому | Когда | Шаблон сообщения |
|---|---|---|
| Внутренний канал инцидента | Сразу после объявления DR | `DR объявлен. Причина: недоступность региона A подтверждена с __:__. IC: __. Сейчас выполняются: подготовка региона B / fencing / восстановление Tier 0. Следующее обновление в __:__.` |
| Гостям на статус-странице | Когда инцидент влияет на поиск/бронирование | `У нас возникли технические проблемы с бронированием. Мы восстанавливаем сервис. Пожалуйста, не повторяйте оплату, если её результат не отображается; проверка операции выполняется системой. Следующее обновление статуса: __:__.` |
| Партнёрам | Если недоступны изменения каталога или инвентаря | `Временная недоступность части партнёрских операций. Не повторяйте массовую загрузку room_counts_by_date до следующего обновления. Сохранённые операции будут сверены после восстановления. Следующее обновление: __:__.` |
| После восстановления | По завершении synthetic tests и открытия трафика | `Основной сценарий бронирования восстановлен в __:__. Продолжается сверка отдельных платежей/уведомлений (если применимо). Все спорные операции проверяются отдельно; итоги и меры профилактики сообщим после разбора.` |

В сообщениях не указываем непроверенный срок полного восстановления и не утверждаем, что платеж успешен, пока Payment Provider не подтвердил результат.

### 4.6. Учения и проверка RTO/RPO

| Периодичность | Учение | Как измеряем результат |
|---|---|---|
| Ежеквартально | Потеря одной Availability Zone в staging: выключить Primary или один набор приложений | Фактический локальный RTO; отсутствие split-brain; соответствие локальным RPO/RTO из п.1 |
| Раз в полгода | Имитация потери региона A и переключение на регион B по runbook | Время от объявления DR до успешного synthetic booking — фактический RTO; разница между последним подтверждённым событием и доступным checkpoint — фактический RPO |
| Раз в полгода | Восстановление БД из backup/PITR после тестового логического удаления | Проверить, что backup пригоден, восстановленная БД проходит integrity checks и ошибка не распространяется с реплики |
| После каждого учения | Прогон runbook инженером, который не писал документ | Независимый исполнитель проходит шаги без устных подсказок; неоднозначные шаги исправляются в документе |

**Критерии успешного DR:** Tier 0 восстановлен в пределах целевого RTO ≤ 12–15 минут; фактическая потеря данных укладывается в допустимый RPO ≤ 5 минут или явно задокументирована как отклонение; нет повторного списания и нет подтверждённых броней сверх room_counts_by_date; тестовые отмена и возврат проходят end-to-end. Если эти условия не выполнены, регион не считается полностью восстановленным даже при зелёных health checks.

### 5. Ключевые метрики

RED используется для API и сервисов; USE — для баз данных, брокера и кэша. Пороговые значения — стартовые SLO/alert-пороги, которые корректируются по baseline после теста. `booking_id`, `asset_id` и `payment_intent_id` нельзя добавлять как labels в метрики с высокой кардинальностью; эти идентификаторы остаются в логах и трейcах.

### 6. Алерты

| Алерт | Условие / окно | Severity | Что означает | Первая реакция / ответственный |
|---|---|---|---|---|
| **Рост ошибок создания брони** | Технические 5xx/timeout на `POST /v1/bookings` > 2% за 5 минут при ≥50 запросах | Critical | Гости не могут начать бронирование | Проверить свежий deploy и ошибки зависимостей; при корреляции с релизом откатить; on-call Booking. |
| **Медленный Hold** | p99 транзакции `Inventory.Hold` > 450 мс за 5 минут либо lock-timeout > 1% за 5 минут (без `SOLD_OUT`) | Warning; Critical при росте 5xx | Увеличивается риск таймаутов и конфликтов на горячем объекте | Разбить latency по shard/property в логах, проверить row locks и DB pool; при hotspot ограничить входной поток по ключу; on-call Inventory. |
| **Деградация платежей или возвратов** | Технические timeout/5xx платежей > 3% за 5 минут **или** старейший `REFUND_PENDING` > 10 минут | Critical | Оплата/возврат не завершаются в ожидаемое время | Разделить проблемы провайдера и своего сервиса; проверить breaker; сверить неоднозначные операции с провайдером; не выполнять слепой повтор capture/refund; on-call Payment. |
| **Репликация PostgreSQL под угрозой** | Sync standby отсутствует > 20 секунд; либо DR replica lag > 45 секунд за 3 минуты (Critical, если > 180 секунд) | Critical для sync; Warning→Critical для DR | При локальном отказе падает запас HA или растёт региональный RPO | Проверить сеть, standby и WAL; эскалировать DBA; не отключать sync-ACK без отдельного решения incident commander. |
| **Kafka отстаёт на критичном пути** | Возраст старейшего события группы Booking > 90 секунд и продолжает расти 3 минуты | Critical | Статусы `HELD`/`REFUND_PENDING` не обновляются своевременно | Проверить consumer health и ошибки обработки; масштабировать группу в пределах партиций; retry/DLT проверять отдельно; on-call Booking. |
| **Поиск устарел** | Возраст последнего применённого `inventory.updated`/`catalog.updated` > 120 секунд в течение 5 минут | Warning | Выдача Search может показывать старую доступность или не видеть обновлённый каталог | Проверить lag Search consumer, DLQ и OpenSearch rejected requests; при восстановлении проиграть события/перестроить индекс; on-call Search. |
| **Просроченные hold не освобождаются** | Есть hold с `expires_at` старше текущего времени на > 2 минуты, и их число растёт 3 минуты | Warning; Critical, если продолжается 10 минут | Номера остаются недоступными после истечения TTL | Проверить Inventory sweeper и блокировки; запустить безопасный повторный проход по `expires_at`; проверить, что уже `CONFIRMED` hold не освобождаются; on-call Inventory. |

Алерты не должны срабатывать на нормальные бизнес-отказы вроде `SOLD_OUT`.

### 7. Логи и трейсы

### Логи

Логи — JSON с полями:
- (request/trace ID).
- временные метки
- связанные ID
- информация для аудита
- источник логов

| Сервис | Что логируем |
|---|---|
| Gateway | route/method, статус, latency, client/partner ID в безопасном виде, результат проверки JWT (без самого токена) |
| Booking | переходы Saga, `booking_id`, шаг/причина, idempotency key в хешированном/маскированном виде, длительность этапа |
| Inventory | `asset_id`, `hold_id`, даты, результат Hold/Confirm/Release, причина отказа и время ожидания блокировки |
| Payment | `payment_intent_id`, provider event ID, тип capture/refund, результат подписи webhook и результат операции; без номера карты/CVV и секретов |
| Search/Catalog | тип запроса, cache hit/miss, версия проекции, применённый event ID, latency индекса/БД |
| Notification | тип уведомления, попытка, результат/код провайдера, задержка; без полного текста письма и PII |
| Audit trail | административные отмены, финансовые статусы и изменения тарифов: кто/что/когда, с ограничением доступа и отдельным сроком хранения |

Не пишем в логи JWT, пароли, полные платёжные данные, секреты, полные адреса/email и тела запросов, содержащие PII. Ошибки провайдера логируются с correlation ID, но без его секретных заголовков.

### Трейсы

Используем OpenTelemetry и W3C Trace Context. Один trace должен связывать синхронный путь `Gateway → Booking → Inventory.Hold → Payment.CreateIntent` и асинхронное продолжение `Payment webhook → payment.events → Booking → Inventory.Confirm`. `traceparent`/correlation context передаётся через HTTP/gRPC metadata и заголовки Kafka; в трейсе сохраняются `booking_id`, `hold_id` и `payment_intent_id` как атрибуты, но не как метки метрик высокой кардинальности.

Для критичного write-path и всех ошибок сохраняем полный трейс; для успешных высокочастотных запросов Search сохраняем полный трейс для 5–10% запросов. Следим за p95/p99 и временем ожидания внешнего провайдера отдельно от пользовательского ожидания 3-D Secure.

## Тестирование

### 8. Нагрузочное тестирование

Профиль взят из ДЗ 4: чтение **45 RPS в среднем / 226 RPS в сезон**, внешний Gateway около **240 RPS** в сезон; запись и webhook — около **21 RPS** суммарно на стороне платформы, `Inventory.Hold` около **6,9 RPS**, webhook Payment около **6,7 RPS**. Расчётная сезонная оценка активных hold — до **6 510** по системе. Доли нагрузки и короткие пиковые всплески нужно подтвердить telemetry после запуска.

| № | Сценарий | Профиль | Длительность | Критерии успеха |
|---:|---|---|---|---|
| 1 | Smoke / baseline | Чтение 45 RPS, входные команды и webhook около 4 RPS | 10–15 мин | API доступно; метрики, логи, трейсы и алерты собираются; тестовые сценарии корректны. |
| 2 | Сезонный целевой пик | Чтение 226 RPS, Gateway до 240 RPS; write/webhook до 21 RPS на платформе | 45–60 мин | Search p99 < 700 мс; `Hold` p99 < 450 мс; `create → HELD` p99 < 1,5 с; технические 5xx < 1%; Kafka lag не растёт постоянно. Пороги — целевые для теста, не достигнутые результаты. |
| 3 | Конкуренция за последний номер | 100 параллельных попыток Hold на один тестовый объект/тип номера/ночь, где осталось 5 номеров | 5–10 мин, несколько прогонов | Не более 5 hold одновременно переходят в действующее состояние; подтверждённые продажи не превышают room_counts_by_date; лишние запросы получают бизнес-отказ, а не двойную бронь. |
| 4 | Spike | Плавная база и затем рост Gateway с 45 до 226 RPS за 30 секунд; отдельно проверяем 1,5× целевого сезонного пика | 10–15 мин | Rate limit возвращает контролируемый `429`, нет каскада 5xx; автоскейлинг Search/Gateway и circuit breaker ведут себя ожидаемо. |
| 5 | Stress | Увеличивать нагрузку от 226 RPS до появления деградации, шагами по 20% | До нахождения предела, затем 10 мин на границе | Найдено фактическое узкое место; нет overbooking или двойного списания; зафиксированы лимиты CPU, pool, OpenSearch и Kafka. |
| 6 | Soak | 75–100% сезонного целевого профиля, включая поиски, создание брони, оплату, отмены и возвраты | 4–6 часов | Нет монотонного роста памяти, connection pool, replication lag или Kafka lag; старые hold закрываются, `REFUND_PENDING` обрабатывается, диск/WAL не приближаются к лимиту. |

Дополнительно в нагрузочном профиле должны быть незавершённые оплаты/3-D Secure, повторные webhook, отмены с refund и поздний `payment.captured` после истечения hold. Условия теста должны проверить, что Saga запускает компенсацию и не объявляет бронь `CONFIRMED`, если Inventory не подтвердил hold.

### 9. Chaos Engineering

Эксперименты проводят на staging с синтетическими данными, ограниченным blast radius, наблюдением on-call и заранее определённой остановкой. В production допускается только отдельно согласованный canary на небольшой доле трафика.

### Эксперимент 1. Отказ Primary PostgreSQL Inventory

- **Steady state:** `Hold` p99 < 450 мс, технические ошибки < 1%, не более room_counts_by_date подтверждённых броней.
- **Гипотеза:** синхронная реплика и failover controller восстановят запись за ≤3 минут; fencing не допустит split-brain.
- **Blast radius:** один staging-кластер БД `Booking`; остальные сервисы и кластер Booking не затрагиваем.
- **Метод:** завершить процесс/инстанс Primary контролируемым chaos-инъектором во время фонового тестового потока Hold.
- **Наблюдаем:** RTO, replication lag, `Hold` p99/5xx, состояние лидера, invariant `confirmed + active holds ≤ room_counts_by_date`.
- **Rollback / abort:** восстановление не произошло за 6 минут (2×RTO), видны два принимающих запись Primary или обнаружено превышение room_counts_by_date — остановить трафик теста, fenced-запись оставить только на одном узле и вручную выполнить сверку.
- **Что узнаём:** фактический RTO локального failover и поведение транзакций в момент смены Primary.

### Эксперимент 2. Задержка/таймаут платёжного провайдера

- **Steady state:** `Inventory.Hold` остаётся в своём p99-бюджете; доля технических 5xx Booking < 1%; нет двойного capture/refund.
- **Гипотеза:** timeout + circuit breaker + отдельный bulkhead Payment изолируют задержку провайдера, не блокируя получение Hold и запросы Search.
- **Blast radius:** staging и sandbox провайдера (или согласованный canary до 5% трафика); воздействие только на исходящие запросы Payment.
- **Метод:** добавить задержку 700–1 000 мс, затем вернуть timeout/ошибку на часть запросов; проверить переход breaker в open/half-open.
- **Наблюдаем:** latency/error rate Payment, Booking `create → HELD`, число открытий breaker, занятость пулов Booking→Payment и Booking→Inventory, retry count.
- **Rollback / abort:** растут ошибки Inventory или Search (не связанный с провайдером путь), ошибки Booking превышают 5% 2 минуты, либо повторяется платёжная операция — прекратить fault injection и выполнить reconciliation платежей.
- **Что узнаём:** достаточны ли timeout, retry и bulkhead; выдерживает ли система неопределённый результат вызова без двойного списания.

### Эксперимент 3. Остановка consumer group Booking в Kafka

- **Steady state:** возраст старейшего события Booking < 30 секунд; доля Saga, застрявших в промежуточных состояниях, ниже согласованного baseline.
- **Гипотеза:** Kafka сохраняет события, а после возвращения consumer-а Booking дочитает `payment.captured`/`payment.failed` и `inventory.released`; идемпотентная обработка не создаёт повторных переходов.
- **Blast radius:**  только тестовый стенд (staging) и только consumer group Booking. Останавливаем её на 5 минут. Producers и остальные consumer groups работают как обычно.
- **Метод:** остановить consumer-ы Booking, создать тестовые оплаты/события, затем вернуть consumer group и измерить время догоняющей обработки.
- **Наблюдаем:** Kafka lag, under-replicated partitions, число броней в `HELD`/`REFUND_PENDING`, успешные `Confirm/Refund`, ошибки дедупликации и DLT.
- **Rollback / abort:** очередь не уменьшается в течение 10 минут после возврата consumer-ов, появились потери событий или несовпадение Payment-провайдера и Booking — прекратить подачу нового тестового трафика и запустить reconciliation.
- **Что узнаём:** время восстановления после накопления lag и корректность at-least-once обработки.

## Безопасность

### 10. Аутентификация / авторизация

- **Клиенты:** OAuth 2.0 / OpenID Connect через внешний Identity Provider; Gateway проверяет подпись JWT, `iss`, `aud`, `exp` и scopes/roles. JWKS кэшируется с ограниченным TTL и обновляется при неизвестном `kid`.
- **Роли:** `guest`, `partner`, `admin`. RBAC: Гость читает и отменяет только собственные брони; `guest_id` берётся из проверенного токена, а не из произвольного поля тела запроса. Партнёр изменяет только свои объекты и room_counts_by_date; действия администратора аудируются.
- **Service-to-service:** внутренние gRPC-вызовы защищены mTLS и отдельными service identities. Inventory принимает команды Hold/Confirm/Release только от разрешённых внутренних сервисов.
- **Payment webhook:** проверка HMAC-подписи по сырому телу запроса, защита от replay (timestamp/допустимое окно, если поддерживает провайдер), дедупликация по `provider_event_id`. Webhook не авторизуется пользовательским JWT.
- **Повторные операции:** все команды, влияющие на деньги или hold, идемпотентны; пользователь не может передать чужой `booking_id` без проверки владельца/прав.

### 11. Шифрование данных

- **В транзите:** TLS 1.2+ для клиента → Gateway; mTLS для внутренних сервисов и закрытых административных endpoints. Репликация БД и межрегиональный трафик также используют шифрование.
- **На диске:** шифрование managed PostgreSQL, OpenSearch, Redis persistent data (если включена), Kafka storage, object storage и всех backup с KMS-ключами; доступ к ключам отделён от доступа к данным.
- **PII:** email, телефон, имя и контактные snapshot-ы бронирования защищены шифрованием хранилища и RBAC; минимизировать поля и срок хранения, доступ к аудит-данным ограничен.
- **Платёжные данные:** Booking.com не хранит номер карты и CVV; используются provider-токен и идентификаторы Payment Intent. В логах — только безопасные идентификаторы и очищенные коды ответа.
- **Секреты:** credentials БД, секрет webhook и настройки интеграции хранятся в Secrets Manager/Vault, не в git и не в логах; ротация выполняется по регламенту.
- **Пароли:** поскольку Identity Provider внешний, Booking.com не хранит пароль. Если локальные учётные записи появятся позже, пароль хранится только как salted hash (Argon2id/bcrypt), а не в обратимо зашифрованном виде.
