# ДЗ 3. Проектирование хранения данных — решение

**Система:** Сервис бронирования отелей (аналог Booking.com) — сервис бронирования отелей, продолжение ДЗ 2.

В ДЗ 2 выбраны сервисы Catalog, Search, Inventory, Booking, Payment, Notification и API Gateway; обмен событиями выполняется через Kafka, а процесс бронирования/отмены координирует Booking Service. В этом решении сохраняется та же декомпозиция. Identity Provider (например, Keycloak/Auth0) внешний: Booking.com проверяет JWT, но не хранит учётные записи пользователей в собственной БД.

## 1. Модель данных

ER-модель: [`diagrams/ER-Diagram.puml`](diagrams/ER-Diagram.puml).

| Сервис | Что хранит | Основные сущности / ключи | Источник истины (SoT) |
|---|---|---|---|
| API Gateway | Постоянные бизнес-данные не хранит; счётчики rate limit и кеш JWKS — временные | Redis keys с TTL; ключи — IP/client и `kid` ключа | Внешний Identity Provider — для аутентификации; Redis не является SoT |
| Catalog Service | Объекты, типы номеров, тарифы и правила отмены | `asset`, `room_types`, `tariff_plans` | PostgreSQL `db_catalog` |
| Search Service | Денормализованные поисковые карточки и подсказки по доступности | `asset_search_document` с гео, удобствами, типами номеров, минимальной ценой и `availabilityHints` | OpenSearch — только read-model, не источник истины |
| Inventory Service | Распределение по датам, активные брони, подтверждения и освобождения | `room_counts_by_date`, `holds`; shard key `asset_id` | PostgreSQL `db_inventory` |
| Booking Service | Брони, snapshot цены, статус Saga, текущий шаг процесса и ссылки на `holdId` / `paymentIntentId` | `bookings`, `idempotency_requests`; shard key `guest_id` | PostgreSQL `db_booking` |
| Payment Service | Платёжные намерения, операции возврата, идемпотентность и обработанные логи webhook | `payment_intents`, `refunds`, `idempotency_keys`, `payment_log` | PostgreSQL `db_payment` |
| Notification Service | В минимальной версии постоянная бизнес-БД не требуется; шаблоны и настройки хранятся в конфигурации | Stateless Kafka consumer; необязательный delivery log — вне критического пути | Kafka + провайдер доставки; повторная доставка не должна приводить к дублированию уведомления |

У каждого сервиса своя БД и собственные миграции. Между БД сервисов нет физических внешних ключей: `asset_id`, `booking_id`, `guest_id`, `hold_id` и `payment_intent_id` — логические ссылки. Поиск читает проекцию из Kafka, но резервирование всегда проверяет Inventory.


## 2. Выбор БД

| Сервис | Форма данных и ключевые запросы | Выбранная БД | Обоснование и компромисс |
|---|---|---|---|
| API Gateway | Краткоживущие счётчики и кеш ключей | **Redis** для rate limit/JWKS; отдельной бизнес-БД нет | Быстрый доступ по ключу и TTL. Потеря кэша допустима: значения восстанавливаются или запрос проходит без кеширования с ограничениями. Идентичности хранятся во внешнем IdP. |
| Catalog | Связи `asset → room_type → tariff_plan`, CRUD, тарифы и JSON-политики | **PostgreSQL** с `JSONB` для гибких правил | Нужны внешние ключи и транзакционные обновления связанного каталога. `JSONB` позволяет не выносить каждую настройку в отдельную таблицу. |
| Search | Геопоиск, фильтры, сортировка, фасеты, пагинация | **OpenSearch** | Инвертированный и геопространственный индексы подходят запросам выдачи. Компромисс — eventual consistency, отсутствие междокументных ACID-транзакций и JOIN как в SQL. |
| Inventory | Слоты по дням и hold по диапазону дат; `Hold/Confirm/Release` | **PostgreSQL** | Нужны атомарная проверка доступности, блокировки строк и уникальные ограничения. Критически важно не допустить overbooking; простая eventual-consistency NoSQL-модель для этого write-path не подходит. |
| Booking | Бронь, состояние Saga, идемпотентные команды и Outbox | **PostgreSQL** | Изменение статуса и outbox-событие фиксируются одной локальной транзакцией; нужны аудит и запросы по идентификатору/гостю. |
| Payment | Payment Intent, возвраты, ключи идемпотентности и дедупликация webhook | **PostgreSQL** | Финансовый журнал и уникальность идентификаторов требуют строгой транзакционной модели и проверяемой истории операций. |
| Notification | Обработка событий и шаблоны | **Без отдельной БД в MVP** | Сервис stateless; Kafka даёт повторное чтение. Если понадобится аудит доставки, отдельный delivery log можно добавить позже, не превращая его в источник состояния брони или платежа. |

Чтобы снизить операционную стоимость на старте, отдельные логические БД PostgreSQL можно разместить в одном managed-кластере, сохраняя независимое владение схемами и доступами. Для масштабирования Inventory и Booking предусматриваются отдельные шарды.

**Почему не другие семейства на текущем этапе:** MongoDB не даёт необходимого выигрыша относительно SQL-связей в Catalog и гарантий транзакционной целостности Booking/Inventory/Payment; Cassandra/Scylla требуют денормализации под запросы и не упрощают атомарный hold на даты; ClickHouse предназначен для аналитики, а не частых точечных изменений hold/платежей; NewSQL может стать вариантом при росте, но сейчас добавит стоимость и сложность без подтверждённой необходимости. OpenSearch и Redis используются строго по своему назначению и не заменяют транзакционные источники истины.

## 3. Шардирование

Схемы: [`diagrams/sharding.puml`](diagrams/sharding.puml).

Для предварительной оценки приняты следующие проектные параметры: 
- 3 млн MAU, 300K DAU
- 1 бронирование на пользователя в месяц
- Пик: x5 в сезон отпусков

При одном бронировании на каждого MAU система создаёт около 3 млн бронирований в месяц, или 100 тыс. в сутки. 

RPS бронирований составляет: 100 000 / 86 400 ≈ 1,16 бронирования/с.

При сезонном коэффициенте ×5 расчётная нагрузка достигает примерно 500 тыс. бронирований в сутки, или 5,79 бронирования/с в среднем за сутки.
Объём таблицы bookings при таком сценарии увеличивается примерно на 36 млн записей в год, до 108 млн записей за три года без учёта удаления и архивирования истории.

Для оценки общего внешнего API-трафика дополнительно принято допущение о 20 API-запросах на DAU в сутки. Оно даёт около 6 млн запросов в сутки, или ~70 RPS в среднем. При сезонном коэффициенте ×5 расчётное значение составляет около ~350 RPS. Чувствительность оценки при 10–30 запросах на DAU в сутки составляет около 35–100 RPS в среднем и 174–521 RPS в сезонном сценарии.

На старте допускается вертикальное масштабирование PostgreSQL и применение read-реплик. Для Booking и Inventory проектируются ключи будущего шардирования, необходимость немедленного физического шардирования не доказана. Для таблицы bookings дополнительно рассматриваются индексация, партиционирование и архивирование истории. Для Inventory ключ asset_id выбран прежде всего для локальности операций над доступностью одного объекта и снижения риска overbooking.

На первом этапе можно начать с вертикального масштабирования и read-реплик; логика маршрутизации и ключи проектируются заранее, а физически включать шарды следует после подтверждения метриками.

### 3.1 Inventory Service

| Решение | Значение |
|---|---|
| Что шардируем | `room_counts_by_date`, `holds`, `outbox` |
| Ключ | `asset_id` |
| Стратегия | Consistent hashing по virtual buckets; 16 виртуальных бакетов поверх 4 физических PostgreSQL-шардов как стартовая проектная конфигурация |
| Почему | Все даты и типы номеров одного объекта размещения попадают на один шард; Hold по нескольким ночам остаётся локальной транзакцией |
| Рост и ребалансировка | Добавить узел, переназначить часть virtual buckets и мигрировать их поэтапно с catch-up записей и переключением маршрутизации |
| Риск | Популярный отель создаёт hotspot. Можно выделить ему отдельный шард/ресурс; нельзя просто «солить» ключ и разнести взаимозависимые слоты без отдельного протокола согласования |

`date` не подходит главным ключом: праздничные даты создают перекос, а hold на несколько ночей пришлось бы выполнять между шардами. `room_type_id` хуже сохраняет локальность всех связанных слотов объекта. Все операции одного `asset_id` маршрутизируются через единый shard router.

### 3.2 Booking Service

| Решение | Значение |
|---|---|
| Что шардируем | `bookings`, `idempotency_requests`, `outbox` |
| Ключ | `guest_id` |
| Стратегия | Consistent hashing; 16 виртуальных бакетов поверх 4 физических PostgreSQL-шардов как стартовая проектная конфигурация |
| Почему | Основной запрос пользователя — «мои брони» — попадает в один шард |
| Поиск по `booking_id` | В идентификаторе брони кодируется `shard_id` (или используется directory `booking_id → shard_id`), чтобы события Payment/Inventory могли найти бронь без полного scatter-gather |
| Риск и компромисс | Поиск всех броней одного отеля может потребовать scatter-gather или отдельной read-модели. Очень активные B2B-аккаунты могут стать hotspot и потребовать отдельного размещения |

Межсервисные шаги Saga не становятся распределённой ACID-транзакцией: каждый сервис фиксирует своё состояние локально, а Booking управляет повторными попытками и компенсациями. Внутри одного шарда связанные изменения выполняются в одной транзакции.

## 4. Кэширование

Диаграмма: [`diagrams/cache.puml`](diagrams/cache.puml).

| Что кэшируем | Уровень и стратегия | TTL | Инвалидация | Допустимое устаревание и цель |
|---|---|---:|---|---|
| Популярные результаты Search | Redis, cache-aside; ключ `search:{hash(normalized_query)}` | 60 секунд | По TTL; не удаляем все варианты поисковых запросов по событию | Устаревшая выдача допустима как подсказка. Hold всегда перепроверяет Inventory; кэш не является разрешением на продажу. |
| Карточка объекта Catalog | Redis, cache-aside; ключ `catalog:asset:{id}` | 10 минут | Удалить ключ при `catalog.updated` для соответствующего объекта | Небольшая задержка допустима для описания, цены на карточке сверяются с актуальными условиями при бронировании. |
| Статус брони при polling | Redis, cache-aside; ключ `booking:status:{bookingId}` | 2 секунды | Booking удаляет ключ после локального изменения статуса; TTL — страховка от пропущенной инвалидации | Секундный лаг допустим в UI; команды и решения Saga читают актуальное состояние из БД, а не из кэша. |
| Индекс времени истечения hold | Redis TTL key как подсказка sweeper | До `expires_at` | Удалить при confirm/release; истечение Redis не меняет состояние само по себе | Только ускорение поиска кандидатов. Авторитетный sweeper сканирует `holds.expires_at` в PostgreSQL, поэтому потеря ключа Redis не теряет hold. |
| Изображения и миниатюры | CDN, cache-by-versioned-URL | 1–7 дней | При замене файла меняется версия URL | Разгружает origin; версии URL позволяют не ждать истечения кэша после изменения изображения. |
| JWKS внешнего IdP | Кэш Gateway в памяти/Redis | 5–15 минут, по политике ротации IdP | Обновление по TTL и при неизвестном `kid` | Сокращает обращения к IdP; при ротации ключей кэш должен обновляться, а не игнорировать новый `kid`. |


## 5. Очереди

Используется **Kafka**: она позволяет нескольким независимым consumer groups получать одни и те же события, сохраняет события для replay при пересборке Search read-model и сглаживает пики нагрузки. Для событий от Catalog, Inventory, Booking и Payment используется **Transactional Outbox**: запись бизнес-изменения и outbox-события выполняется в одной транзакции; publisher доставляет событие в Kafka после commit.

| Topic | События | Producer | Consumers | Partition key / смысл |
|---|---|---|---|---|
| `catalog.events` | `catalog.updated` | Catalog Service | Search Service | `asset_id`; новые/изменённые карточки, типы номеров и тарифы |
| `inventory.events` | `inventory.updated`, `inventory.held`, `inventory.confirmed`, `inventory.released` | Inventory Service | Search Service; Booking Service слушает `inventory.released` | `asset_id`; изменения доступности. `inventory.released` также завершает ветку истечения hold в Saga |
| `booking.events` | `booking.created`, `booking.held`, `booking.confirmed`, `booking.cancellation_requested`, `booking.refund_pending`, `booking.cancelled`, `booking.failed` | Booking Service | Notification Service | `booking_id`; события жизненного цикла брони и статуса для пользователя |
| `payment.events` | `payment.captured`, `payment.failed`, `payment.refunded`, `payment.refund_failed` | Payment Service | Booking Service; Notification Service | `booking_id` (если событие относится к брони); результаты оплаты и возврата |

**Search подписан на `catalog.events` и `inventory.events`**, а не использует `booking.confirmed`/`booking.cancelled` как единственный источник доступности. Так новые объекты и тарифы попадут в индекс, а hold/confirm/release будут менять подсказки доступности. Это всё равно eventually consistent: поисковая выдача не резервирует номер, а итоговое решение принимает Inventory.

### Надёжность consumer-ов

- У каждого события есть `event_id`, `event_type`, `schema_version`, `occurred_at`, `partition key` и payload; потребители дедуплицируют по `event_id`.
- Сообщения обрабатываются как **at-least-once**: код consumer-а должен быть идемпотентен.
- Для временных ошибок — ограниченные retry с backoff; после исчерпания попыток — отдельный DLT и alert **на каждую consumer group**, чтобы сбой Search не задерживал Notification.
- Kafka используется для фактов о завершившихся изменениях. Команды `Hold`, `Confirm`, `Release` и критические шаги Saga вызываются синхронно по gRPC, когда нужен непосредственный результат.

## 6. CAP trade-offs

CAP описывает выбор при сетевом разделении: для распределённого контура нельзя одновременно гарантировать строгую согласованность (C) и доступность каждого запроса (A), сохраняя устойчивость к partition (P). В Booking.com разные подсистемы имеют разные приоритеты.

| Контур | Предпочтение при partition | Что теряем / почему |
|---|---|---|
| Inventory write path | **CP-oriented** | Если нельзя надёжно проверить и зафиксировать слоты, `Hold` завершается ошибкой/503, а не подтверждается по устаревшему кэшу. Важнее не продать один номер дважды. |
| Booking и Payment | **CP-oriented** для локального состояния, idempotency и финансового журнала | При недоступности primary нельзя объявлять неподтверждённую операцию успешной. Брони и платежи могут временно ждать восстановления. |
| Search / OpenSearch | **AP-oriented read model** | Выдача остаётся доступной при задержке проекции, но может содержать устаревшую доступность. Это допустимо, потому что окончательное решение выполняет Inventory. |
| Redis cache | Best effort / **AP-поведение кэша** | Кэш может быть устаревшим или недоступным; при необходимости запрос идёт в источник данных. Redis не хранит единственную копию hold или платёжного состояния. |
| Kafka и Saga между сервисами | **Eventual consistency** между локальными транзакциями | Нет мгновенной глобальной атомарности. Система показывает `REFUND_PENDING`/`CANCELLATION_PENDING`, пока не пришёл подтверждённый результат, и использует retry, дедупликацию и компенсации. |

Основной компромисс Booking.com: строгая проверка при записи брони/платежа и допускаемая задержка в поисковой read-модели.
