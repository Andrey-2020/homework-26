# ДЗ 6. Проектная работа — решение

## Выбранная тема

**GroupWave** — мессенджер для личных диалогов и групповых чатов. Клиенты: web, Android и iOS. Главный архитектурный сценарий — быстро принять сообщение, надёжно сохранить его, асинхронно доставить участникам и позволить догнать историю после переподключения.

### Проектные допущения и масштаб

| Параметр | Принятое значение | Основание |
|---|---:|---|
| Зарегистрированные пользователи | 8 млн | проектная аудитория |
| MAU | 4 млн | 50% зарегистрированных |
| DAU | 1,2 млн | 30% MAU |
| Отправок от одного DAU | 18 сообщений/сутки | средний сценарий смешанного личного и группового общения |
| Доля сообщений с медиа | 3% | основная нагрузка — текст; медиа реже, но тяжелее |
| Средний размер медиаобъекта | 180 KB | сжатое фото/небольшой файл, а не видео |
| Среднее число получателей одного сообщения | 2,4 | смесь личных и небольших групповых чатов, без массовых каналов |
| Пиковый коэффициент | ×4 | вечерний/сезонный всплеск |
| Среднее число подключённых устройств на онлайн-пользователя | 1,15 | часть пользователей подключена с двух устройств |

Расчётные производные:

- Сообщений в сутки: `1 200 000 × 18 = 21 600 000`.
- Средняя скорость отправки: `21 600 000 / 86 400 = 250 сообщений/с`.
- Пиковая скорость отправки: `250 × 4 = 1 000 сообщений/с`.
- Доставок получателям: `21 600 000 × 2,4 = 51 840 000/сутки`, или `600 доставок/с` в среднем и `2 400/с` в пике.
- Медиаобъектов: `21 600 000 × 3% = 648 000/сутки`.
- Загрузка медиа: `648 000 × 180 KB = 116,64 GB/сутки`.

### 1.3. Риски и ограничения

- При всплеске активности в одной группе возникает hot partition и рост задержки доставки.
- Kafka и DynamoDB Streams обеспечивают повторную доставку событий; обработчики обязаны быть идемпотентными.
- Зависимость от FCM/APNs может задержать push, но не должна блокировать сохранение сообщения.
- Потеря региона не должна приводить к двум одновременно активным write-регионам: перед переключением нужен fencing старого writer.
- В MVP не реализуется сквозное шифрование (E2EE). Применяется TLS и шифрование на стороне хранилищ; это не эквивалентно E2EE.
- Медиа — существенная статья трафика; нужна политика срока хранения и CDN.
- Допущения RPS и размера данных необходимо уточнить по телеметрии после запуска.

### 1.4. Backlog — вне scope

- аудио- и видеозвонки;
- сквозное E2EE, управление ключами и безопасное добавление новых устройств;
- публичные каналы на десятки тысяч/миллионы подписчиков;
- боты, мини-приложения и интеграции сторонних разработчиков;
- исчезающие сообщения и полное редактирование истории на всех устройствах;
- multi-region active-active запись;
- расширенный полнотекстовый поиск по всем сообщениям;
- бизнес-аналитика и экспорт больших архивов.

## 2. Концептуальная архитектура

### 2.1. C4 Context

Исходник: [`diagrams/c4-context.puml`](diagrams/c4-context.puml).

**Пользователи:** обычный пользователь web/iOS/Android и оператор платформы. **Внешние интеграции:** FCM для Android push, APNs для iOS push, почтовый провайдер для подтверждения email и восстановления доступа, AWS object storage/CDN для медиа.

Клиент использует HTTPS для REST-операций и WSS для realtime-обмена. Оператор работает через отдельный административный путь и усиленную авторизацию.

### 2.2. C4 Container

Исходник: [`diagrams/c4-containers.puml`](diagrams/c4-containers.png).

| Контейнер | Ответственность | Хранилище/интеграция |
|---|---|---|
| API Gateway | REST ingress, проверка JWT, rate limit, маршрутизация HTTP | WAF/ALB; не хранит бизнес-данные |
| Realtime Gateway | Долгие WSS-соединения, аутентификация соединения, приём/отправка realtime frames | горизонтально масштабируемые stateless-инстансы; Redis используется для поиска активного gateway |
| Identity Service | Пользователи, учётные данные, refresh-сессии, устройство и роли | PostgreSQL Multi-AZ |
| Chat Service | Создание групп, состав участников, роли, mute-настройки и права доступа | PostgreSQL Multi-AZ; кэш небольших read-моделей в Redis |
| Message Service | Проверка прав через Chat Service/кэш, запись сообщения, выдача истории и курсоров | DynamoDB; сообщение хранится один раз на чат, без копии на каждого получателя |
| Event Relay + Kafka | Публикация события о сохранённом сообщении и доставка заданий consumer-группам | DynamoDB Streams → relay → MSK/Kafka |
| Delivery Workers | Fan-out по участникам чата, отправка в активные WSS-соединения, постановка офлайн-push | Kafka consumer group; Redis Presence; Chat Service |
| Presence Service | Online-состояние и соответствие user/device → realtime gateway | Redis TTL; потеря данных безопасна |
| Media Service | Выдача короткоживущих pre-signed URL, проверка метаданных файла | S3 + CloudFront; содержимое не проходит через приложение |
| Push Service | Отправка push для офлайн-устройств и повторная обработка временных ошибок | Kafka topic `push.jobs`, FCM/APNs |

### Архитектурный стиль

Используется **сервисная/event-driven архитектура** с отдельным realtime ingress. Синхронными оставлены операции, где клиенту нужен непосредственный ответ: авторизация, права доступа, создание группы, запрос истории и выдача upload URL. Рассылка сообщения участникам, push и обновление вторичных проекций идут асинхронно через Kafka.

Это позволяет изолировать всплески fan-out от сохранения сообщения и отдельно масштабировать WebSocket-соединения, запись, доставку и push. Не делаем микросервис на каждую мелкую сущность: Identity, Chat, Message, Presence, Media и Push имеют отдельные границы ответственности, но модель остаётся понятной для учебного проекта.

## 3. Сайзинг

Все показатели — расчётная модель. Peak factor ×4 используется один раз, не умножается повторно на те же данные.

### 3.1. RPS

Формула: `RPS = запросов/сутки ÷ 86 400`; пик = `среднее × 4`.

| Операция | Допущение | Запросов/сутки | Среднее RPS | Пик RPS |
|---|---|---:|---:|---:|
| Отправка сообщений через WSS | 1,2 млн DAU × 18 сообщений | 21,6 млн | 250 | 1 000 |
| Получение истории чата | 1,2 млн DAU × 6 страниц | 7,2 млн | 83,3 | 333 |
| Получение списка чатов | 1,2 млн DAU × 4 раза | 4,8 млн | 55,6 | 222 |
| Операции группы/участников | 0,4 операции на DAU | 480 тыс. | 5,6 | 22 |
| Получение upload URL | 3% от отправок | 648 тыс. | 7,5 | 30 |
| **Пользовательские запросы** | Сумма выше, heartbeat не включён | **34,73 млн** | **402** | **1 607** |
| Fan-out доставок | 21,6 млн × 2,4 получателя | 51,84 млн | 600 событий/с | 2 400 событий/с |

Fan-out — внутренние события, а не дополнительные запросы пользователя. Heartbeat также отдельно: `216 000 одновременных пользователей × 1,15 устройства ÷ 30 s ≈ 8 280 ping/pong циклов/с`. Это WebSocket control frames, а не HTTP-запросы.

Одновременные соединения: `1,2 млн DAU × 18% онлайн одновременно × 1,15 устройства ≈ 248 400 WSS-соединений`. Целевая ёмкость 320 000 оставляет около 29% запаса.

### 3.2. Хранилище

| Данные | Формула | 1 год | 3 года / steady state |
|---|---|---:|---:|
| Сообщения (raw, объём генерации) | 21,6 млн/сутки × 0,8 KB × 365 дней | 6,31 TB | 18,92 TB было бы накоплено за 3 года без удаления |
| Сообщения с индексами/overhead | raw × 1,35 | 8,52 TB | 25,54 TB без TTL; **в расчёте стоимости используется retention 2 года: 17,03 TB** |
| Медиа | 648 тыс./сутки × 180 KB × 365 дней | 42,57 TB | 42,57 TB при retention 1 год; объём не растёт дальше при удалении старых объектов |
| Из них горячие медиа | 116,64 GB/сутки × 30 дней | 3,50 TB | 3,50 TB |
| Медиа старше 30 дней | общий годовой объём − hot | 39,07 TB | 39,07 TB |
| Identity, группы, членства | проектная оценка по 8 млн учётных записей и связям | <100 GB | <150 GB |
| Kafka | 51,84 млн доставок × 250 B × 3 дня × RF=3 | около 117 GB | около 117 GB + запас; retention ограничен |
| Redis Presence | 250 тыс. соединений + TTL-ключи и metadata | 3–5 GB RAM | 3–5 GB RAM |

В таблице сообщений 0,8 KB — усреднённый размер сериализованной записи с метаданными. Индексный множитель 1,35 — допущение для расчёта billable footprint, а не точная характеристика DynamoDB. Так как NFR устанавливает retention сообщений 2 года, после выхода на steady state хранилище содержит примерно два годовых объёма: `2 × 6,31 = 12,62 TB raw`, или `12,62 × 1,35 ≈ 17,03 TB` с overhead. Число за 3 года без удаления приводится только для понимания объёма генерации и не используется для расчёта тарифа. Медиа объекты не копируются в каждую группу/получателю — хранится один объект, а пользователям выдаётся доступ по авторизованной ссылке.

### 3.3. Bandwidth

| Поток | Формула | Оценка |
|---|---|---:|
| Входящие payload сообщений | 21,6 млн × 1,5 KB | 32,4 GB/сутки |
| Ответы истории | 7,2 млн страниц × 30 сообщений × 1 KB на сообщение | 216 GB/сутки |
| WSS-доставка текста | 51,84 млн доставок × 1 KB | 51,84 GB/сутки |
| Загрузка медиа | 648 тыс. × 180 KB | 116,64 GB/сутки inbound |
| Скачивание медиа получателями | 116,64 GB × 2,4 получателя | 279,94 GB/сутки outbound |
| Прочие ответы/заголовки | резервная оценка | 6 GB/сутки |
| **Общий исходящий трафик** | 216 + 51,84 + 279,94 + 6 | **около 554 GB/сутки** |

Месячный трафик к пользователям: `554 × 30 ≈ 16,6 TB`. Средняя полоса: `554 GB × 8 / 86 400 ≈ 51,3 Mbit/s`. Пиковая ×4 — примерно 205 Mbit/s; с 30% запаса целевой проектный egress — **около 270 Mbit/s, округляем до 300 Mbit/s**. Входящий поток текста и медиа — около 149 GB/сутки, или 14 Mbit/s в среднем и ~56 Mbit/s в пике; для ingress закладываем 75 Mbit/s.

На медиа используется CloudFront. Cache hit 85% снижает количество обращений к S3, но клиентский egress CDN всё равно считается по объёму данных, отданных пользователям.

### 3.4. Ресурсы

Это начальная конфигурация для целевого сезонного пика, подлежащая проверке нагрузочным тестом. Она предусматривает запас мощности и работу минимум в трёх AZ.

| Компонент | Конфигурация | Количество | Обоснование |
|---|---|---:|---|
| Realtime Gateway | 4 vCPU, 16 GB RAM | 8 | цель до 40 тыс. долгих соединений на узел; всего 320 тыс. |
| Message Service | 4 vCPU, 16 GB RAM | 6 | 1 000 записей/с в пике и синхронная проверка прав/сохранение |
| Delivery Workers | 4 vCPU, 16 GB RAM | 8 | 2 400 fan-out событий/с в пике и запас на lag |
| Identity Service | 2 vCPU, 8 GB RAM | 3 | stateless application, 3 AZ |
| Chat Service | 2 vCPU, 8 GB RAM | 4 | membership/ACL-запросы и group metadata |
| Presence Service | 2 vCPU, 8 GB RAM | 3 | операции по connection registry |
| Media Service | 2 vCPU, 8 GB RAM | 3 | выдача presigned URL и проверка метаданных, не проксирует байты |
| Push Service | 2 vCPU, 8 GB RAM | 3 | интеграции FCM/APNs, масштабирование по очереди |
| **Итого app compute** | 22 узла 4-vCPU + 16 узлов 2-vCPU | **38 узлов / 120 vCPU** | автоскейлинг worker'ов и gateway по метрикам |
| PostgreSQL | 2 Multi-AZ кластера, primary + standby/reader, по 2 vCPU | 2 кластера | Identity и Chat metadata, не сообщения |
| DynamoDB | on-demand, PITR; глобальная таблица/асинхронная региональная копия для DR | managed | горизонтальное масштабирование хранения сообщений |
| Kafka / MSK | 3 брокера, RF=3, `min.insync.replicas=2` | 1 кластер в основном регионе | durable delivery events, несколько consumer groups |
| Redis | 3 узла, около 8 GB RAM каждый | 1 кластер | Presence, routing и ограниченные TTL-кэши; не source of truth |
| S3 + CloudFront | 30 дней Standard, далее Standard-IA, удаление по retention | managed | прямые upload/download, CDN cache |

На начальном этапе DynamoDB on-demand снимает необходимость вручную задавать число шардов. Физические параметры и лимиты необходимо подтвердить load test; таблица ресурсов — стартовый sizing, а не гарантия производительности провайдера.

## 4. Хранение данных

### 4.1. Выбор БД

| Данные | Технология | Причина | Осознанный компромисс |
|---|---|---|---|
| Учётные записи, refresh sessions | PostgreSQL | уникальность email, транзакции и связи между пользователем и устройствами | горизонтальное шардирование не нужно на старте |
| Чаты, участники, роли, mute | PostgreSQL | реляционные связи и транзакционные изменения membership | перед чтением сообщения выполняется проверка членства; глобальные JOIN между сервисами не используются |
| Сообщения и курсоры истории | DynamoDB | горизонтальная масштабируемость, точечная запись и запрос истории по partition key + sort key | сложный полнотекстовый поиск не является основным сценарием; нет SQL JOIN |
| Presence и gateway routing | Redis | быстрый key/value и TTL на короткоживущие online-ключи | данные эфемерные, Redis не является источником истины истории |
| Медиафайлы | S3 | дешёвое объектное хранение, lifecycle и presigned URL | объектные метаданные в S3 не заменяют ACL, доступ выдаёт Media Service |
| Очередь доставки | Kafka / MSK | буферизация fan-out, replay, независимые consumer groups | eventual consistency и at-least-once, поэтому нужна идемпотентность |

### 4.2. Модель данных

Основные сущности:

- `users(user_id, email, password_hash/identity_ref, status, created_at)` — PostgreSQL Identity.
- `devices(device_id, user_id, push_token, platform, refresh_session_id, last_seen_at)` — устройства пользователя.
- `chats(chat_id, type, title, owner_id, created_at, status)` — PostgreSQL Chat.
- `chat_members(chat_id, user_id, role, joined_at, muted_until, status)` — участники и права доступа.
- DynamoDB `messages`: `PK = CHAT#{chat_id}#BUCKET#{YYYYMM}`, `SK = {server_timestamp}#{message_id}`; атрибуты `sender_id`, `text`, `media_ids`, `reply_to`, `edited_at`, `deleted_at`, `client_message_id`.
- DynamoDB `message_dedup`: ключ `(sender_id, client_message_id)` с TTL, чтобы сетевой retry не создавал повторную запись.
- DynamoDB `read_cursors`: ключ `(chat_id, user_id)`, `last_delivered_cursor`, `last_read_cursor`, `updated_at`.
- S3 `media/{tenant}/{media_id}` — объект, его размер/checksum/content type и владелец хранятся в metadata-таблице Media Service.

Логические ссылки `user_id`, `chat_id` и `message_id` между сервисами не являются физическими внешними ключами в одной БД. Приложение проверяет права через Chat Service; кэш ACL имеет небольшой TTL и инвалидируется при изменении состава группы.

Схема: [`diagrams/data-model-sharding.puml`](diagrams/data-model-sharding.puml).

### 4.3. Шардирование и partitioning

У DynamoDB физическое распределение управляется сервисом. В проекте явно задаётся логический ключ и временной bucket, чтобы история одного чата читалась упорядоченными диапазонами и бесконечная история не накапливалась в одном logical partition.

| Что | Ключ | Стратегия | Риск и мера |
|---|---|---|---|
| `messages` | `CHAT#{chat_id}#BUCKET#{YYYYMM}` / sort key timestamp + message ID | hash partitioning DynamoDB, отдельная partition key на чат и календарный месяц | очень активный чат может стать hot partition; ограничить group до 300, ввести rate limit на чат, следить за throttling и при подтверждённой необходимости вводить sub-bucket |
| `chat_members` | `chat_id` в PostgreSQL | на старте одна Multi-AZ БД, индексы `(chat_id, user_id)` и `(user_id, chat_id)` | не шардировать заранее без метрик; если таблица станет узким местом — hash-sharding по `chat_id`, чтобы состав группы был локальным |
| `read_cursors` | `chat_id + user_id` | DynamoDB key/value | курсор хранится один на пользователя и чат, а не на каждое устройство |

Сначала масштабируются индексы/throughput и compute. Физическое разделение PostgreSQL включается только после измерений. DynamoDB уже распределяет данные по партициям на основе ключа; ручной массив из десятков БД в MVP не нужен.

### 4.4. Кэширование

| Что | Кэш | Стратегия | TTL | Инвалидация |
|---|---|---|---|---|
| Presence и активные gateway подключения | Redis | запись при connect/heartbeat, TTL | 90 секунд без heartbeat | TTL и явный delete при disconnect |
| Метаданные чата/список участников | Redis | cache-aside | 30–60 секунд | событие `chat.membership_changed` удаляет/обновляет ключ |
| Список чатов пользователя | Redis | cache-aside | 30 секунд | invalidation на создании группы/изменении membership |
| Медиа | CloudFront | CDN cache по versioned object key | 1–7 дней для неизменяемых объектов | новый `media_id`/version при замене файла |
| История сообщений | Не кэшируем централизованно по умолчанию | запрос в DynamoDB по cursor | — | избегаем сложной инвалидации персональной истории; позже можно кэшировать короткие head-страницы |

Кэш Presence — подсказка для маршрутизации, а не гарантия онлайн-доставки: если gateway недоступен, Delivery Worker отправляет push или оставляет сообщение доступным для синхронизации. Нельзя использовать Redis как единственное хранилище сообщения, членства или прочитанного cursor.

## 5. Взаимодействие

### 5.1. Основной поток отправки

Схема: [`diagrams/message-delivery.puml`](diagrams/message-delivery.puml).

1. Клиент устанавливает WSS-соединение через Realtime Gateway и передаёт access token в безопасном handshake/header механизме.
2. При `message.send` Gateway проверяет формат и передаёт команду Message Service.
3. Message Service проверяет membership/право писать, проверяет `clientMessageId` на дубликат и сохраняет сообщение в DynamoDB.
4. После успешной записи сервер отправляет отправителю `message.accepted` с `messageId` и cursor. До подтверждения сохранения ACK не выдаётся.
5. DynamoDB Streams relay публикует `message.persisted` в Kafka. Delivery Workers читают сообщение и получают список участников чата.
6. Для активных устройств worker отправляет `message.new` в соответствующий Realtime Gateway. Для офлайн-устройств публикуется `push.jobs`, если уведомления не выключены.
7. При переподключении клиент вызывает `GET /v1/chats/{chatId}/messages?cursor=...` и догружает историю.

Семантика доставки — **at-least-once**: сообщение может прийти повторно при retry или replay, поэтому клиент дедуплицирует по `messageId`. Система не обещает end-to-end exactly-once доставку.

### 5.2. Протоколы

| Связь | Протокол | Причина |
|---|---|---|
| Клиент → API Gateway | HTTPS REST | управление чатами, приглашения, история, upload URL |
| Клиент ↔ Realtime Gateway | WSS/WebSocket | low-latency двунаправленные сообщения, delivery, receipts, heartbeat |
| API Gateway → Identity/Chat/Media | HTTP/gRPC внутри VPC | запрос-ответ и явные контракты; можно начать с HTTP/JSON для простоты MVP |
| Message Store → Event Relay | DynamoDB Streams | публикуем только уже зафиксированные изменения, уменьшаем риск dual-write |
| Event Relay → Kafka | Kafka protocol | буферизация и несколько consumer groups |
| Delivery Workers → Presence/Chat | внутренний HTTP/gRPC | получить gateway и membership |
| Push Service → FCM/APNs | HTTPS/HTTP2 | внешний интерфейс поставщиков push |
| Client ↔ S3/CloudFront | HTTPS с временными URL | файлы не идут через app-инстансы |

### 5.3. Ключевые API-контракты

Полные REST-контракты: [`api/openapi.yaml`](api/openapi.yaml).

Ключевые операции:

1. `POST /v1/chats` — создать группу.
2. `GET /v1/chats/{chatId}/messages` — получить историю по cursor.
3. `POST /v1/media/upload-url` — получить presigned URL на загрузку.
4. `POST /v1/chats/{chatId}/members` — пригласить участника (только admin/owner).
5. `POST /v1/chats/sync` — догнать историю по нескольким cursor после reconnect.

### WebSocket contract: `message.send`

Клиент отправляет frame:

```json
{
  "type": "message.send",
  "requestId": "req_d2a41f",
  "clientMessageId": "01J8Y6R4P4D8Z5H7B4M9N2QK10",
  "chatId": "chat_73a1",
  "text": "Встречаемся у входа в 19:30",
  "mediaIds": [],
  "replyToMessageId": null
}
```

После успешной записи сервер возвращает:

```json
{
  "type": "message.accepted",
  "requestId": "req_d2a41f",
  "messageId": "msg_91bd",
  "serverTime": "2026-10-24T18:30:12Z",
  "cursor": "2026-10-24T18:30:12Z#msg_91bd"
}
```

Получатель получает `message.new` с `messageId`, `chatId`, автором, временем сервера, текстом и ссылками на медиа. Клиент подтверждает получение курсором (`delivery.cursor`), а прочтение — `read.cursor`. Операции идемпотентны по `clientMessageId`/монотонному cursor.

## 6. Надёжность

### 6.1. Целевые RTO/RPO

RTO/RPO ниже — проектные цели для локального отказа и полной потери региона; они должны проверяться учениями, а не считаться достигнутыми автоматически.

| Компонент | Критичность | Локальный RPO/RTO | Региональный DR RPO/RTO | Обоснование |
|---|---|---|---|---|
| Message Store (DynamoDB) | Tier 0 | практически 0 / <5 мин | ≤1 мин / ≤30 мин | принятое сообщение не должно исчезать; cross-region replica и идемпотентные повторы |
| Chat metadata (PostgreSQL) | Tier 0 | 0 при Multi-AZ / <5 мин | ≤5 мин / ≤30 мин | без membership нельзя безопасно читать/писать в группу |
| Identity (PostgreSQL) | Tier 1 | 0 при Multi-AZ / <10 мин | ≤5 мин / ≤45 мин | отказ мешает новому входу, действующие короткие JWT могут жить до истечения |
| Kafka | Tier 0 для доставки | подтверждённые записи сохраняются при потере одного брокера / <5 мин | ≤5 мин / ≤30 мин | RF=3, `acks=all`, `min.insync.replicas=2`; региональная реплика асинхронная |
| Presence/Redis | Tier 2 | данные не являются SoT / <5 мин | RPO не применим / <15 мин | presence восстанавливается из подключений и heartbeat |
| Media/S3 | Tier 1 | высокая durable storage; target RPO≈0 в регионе / <15 мин | ≤15 мин / ≤60 мин | Cross-Region Replication; ссылка на файл может обновляться, сообщение остаётся в store |
| Delivery/Push workers | Tier 1 | состояние в Kafka, локальный RPO не применим / <10 мин | ≤5 мин / ≤45 мин | consumer group можно пересоздать и переиграть события |
| API/Realtime Gateway | Tier 1 | нет бизнес-данных / <5 мин | нет бизнес-данных / <30 мин | пересоздаётся из образа; клиент переподключается и синхронизирует курсор |

### 6.2. Репликация

- **DynamoDB:** multi-AZ durability силами managed сервиса; point-in-time recovery включён. Для DR — Global Tables/региональная реплика в режиме одного активного writer: приложение не пишет в два региона одновременно.
- **PostgreSQL:** Multi-AZ primary/standby в основном регионе; асинхронная read-replica или backup copy в DR-регионе.
- **Kafka:** replication factor 3 внутри региона, producer `acks=all`, `min.insync.replicas=2`; асинхронная межрегиональная репликация.
- **S3:** versioning, lifecycle, Cross-Region Replication для объектов; отдельные политики хранения и запрет публичного чтения бакета.
- **Redis:** кластер с репликами/авто-failover, но наличие ключа не доказывает факт доставки.

### 6.3. План DR — текстовый runbook

**Когда объявлять DR:** Incident Commander объявляет DR, если регион недоступен с двух независимых точек мониторинга более 5 минут и штатное восстановление AZ/managed failover не вернуло критичный поток. DBA/SRE могут рекомендовать DR, но не переключают write-регион независимо от Incident Commander.

**Роли:** Incident Commander руководит инцидентом и решением о переключении; SRE отвечает за сеть, DNS, Gateway и масштабирование; DBA отвечает за PostgreSQL/DynamoDB и проверку replication lag; владелец Message/Chat подтверждает согласованность; ответственный за коммуникации публикует статус для пользователей и операторов.

**Порядок восстановления:**

1. Зафиксировать инцидент, время начала, затронутые сервисы и последние здоровые метрики.
2. Подтвердить потерю региона независимыми проверками; исключить кратковременную сетевую ошибку.
3. Заморозить запись в старый регион на уровне routing/credentials и включить fencing, чтобы не возникли два writer.
4. Проверить доступность сети, IAM, KMS-ключей, секретов, DNS и межрегиональных маршрутов в регионе B.
5. Проверить lag репликации и доступность последней копии данных; при наличии сомнений не открывать запись до фиксации точки восстановления.
6. Переключить DynamoDB table/конфигурацию на DR-реплику; проверить чтение/запись тестового сообщения и идемпотентность.
7. Promote PostgreSQL read replica или восстановить последнюю пригодную копию; проверить users/chats/membership и уникальные ограничения.
8. Поднять Kafka consumers/producers в регионе B и проверить наличие нужных топиков; продолжить обработку с безопасным replay по event ID, не полагаясь на совпадение Kafka offsets между регионами.
9. Запустить Message Service, Chat/Identity, Realtime Gateway, Delivery Workers, Media и Push в порядке зависимости; сначала минимальная рабочая ёмкость, затем масштабирование.
10. Переключить DNS/edge на регион B с постепенным увеличением трафика; контролировать ошибки и connection reconnect.
11. Выполнить синтетический сценарий: login → открыть группу → отправить сообщение → получить его вторым участником → отключить/подключить клиента → догнать историю → проверить медиа и push.
12. Сверить число сохранённых сообщений и потоков, Kafka lag, idempotency conflicts, membership ACL и DR-репликацию; сообщить о восстановлении только после успешного smoke test.

**Коммуникация:** внутреннее сообщение содержит время инцидента, затронутую функциональность, выбранный регион, целевой срок следующего обновления и ссылку на инцидент. Пользовательское сообщение не обещает точное время восстановления: сообщает, что доставка/подключение деградированы, а история синхронизируется после восстановления. Для операторов и поддержки используется отдельный статус о восстановлении push/media.

**Возврат в основной регион:** только после стабилизации, сверки данных и отдельного change window. Не переключать writer обратно автоматически сразу после восстановления первичного региона.

**Учения:** раз в квартал выполняется game day на staging: потеря одной AZ, затем отдельный tabletop/pilot test полного регионального переключения. Измеряются фактические RTO/RPO, runbook прогоняет инженер, который его не писал.

## 7. Безопасность

### 7.1. Аутентификация и авторизация

- OIDC для входа, access JWT живёт 15 минут, refresh token ротируется и привязывается к устройству.
- API Gateway проверяет подпись/issuer/audience токена; Realtime Gateway проверяет токен во время WSS handshake. Токены не передаются в query string и не пишутся в логи.
- RBAC: `owner`, `admin`, `member`; доступ к чату дополнительно проверяется по membership, одной роли недостаточно.
- Приглашать участников и менять роли могут только owner/admin; читать и писать сообщения могут только активные участники.
- Rate limiting по user/device/IP защищает login, invite, send и upload URL от abuse.
- Подписанные ссылки S3 ограничены объектом, операцией, размером и сроком действия (например, 5 минут на PUT URL); bucket закрыт от публичного доступа.
- Для административного доступа — отдельная роль, MFA и аудит действий.

### 7.2. Шифрование и секреты

- TLS 1.2+ для HTTPS/WSS и внутренних соединений; mTLS между критичными сервисами при поддержке платформы.
- Шифрование в покое для PostgreSQL, DynamoDB, S3, Kafka и бэкапов с использованием KMS-managed keys.
- Секреты/пароли/ключи провайдеров хранятся в Secrets Manager/Parameter Store, доступны по IAM role, не в переменных репозитория.
- Refresh tokens хранятся хэшированными; пароли — через Argon2id/bcrypt с индивидуальной солью.
- Медиа проверяются по размеру, MIME/signature и checksum; подозрительные загрузки попадают в quarantine до антивирусной проверки.
- В логи не записываются пароль, access/refresh token, содержимое приватных сообщений и push token в открытом виде.
- E2EE не заявляется: сервер может обработать текст для доставки и moderation/abuse controls. Реализация настоящего E2EE вынесена в backlog.

## 8. Observability

### 8.1. Ключевые метрики (RED/USE + бизнес)

| № | Метрика | Тип | Где | Зачем |
|---:|---|---|---|---|
| 1 | `message_send_requests_total` по исходу | RED/Rate | Gateway/Message | базовый поток и доля успешных отправок |
| 2 | `message_persist_duration_seconds` p50/p95/p99 | RED/Duration | latency, которую видит отправитель |
| 3 | `message_send_errors_total` по причине | RED/Errors | разделить ACL/business reject и 5xx/timeout |
| 4 | `active_websocket_connections` | Capacity | Realtime Gateway | сверка с пределом 320k |
| 5 | `websocket_reconnect_rate` | Rate | Realtime Gateway | reconnect storm после сетевого/регионального сбоя |
| 6 | `online_delivery_latency_seconds` p95/p99 | RED | Delivery/Gateway | задержка получения сообщения онлайн-получателем |
| 7 | `delivery_events_consumer_lag_seconds` | Saturation | Kafka consumer group | очередь успевает или растёт отставание |
| 8 | `delivery_retry_total` / `delivery_dlt_total` | Errors | Delivery Workers | ошибки доставки и сообщения, требующие ручного разбора |
| 9 | DynamoDB throttled requests | USE/Errors | Message Store | недостаток throughput/hot partition |
| 10 | DynamoDB consumed read/write capacity | USE | Message Store | прогноз роста и capacity hotspots |
| 11 | `postgres_connection_pool_utilization` | USE | Identity/Chat | насыщение пула до отказа |
| 12 | Redis memory/eviction rate | USE | Presence | вероятность массового исчезновения routing hints |
| 13 | `media_upload_success_ratio` | Business | Media/S3 | контроль пути загрузки вложения |
| 14 | `messages_accepted_per_minute` | Business | Message Service | реальная полезная нагрузка системы |

Ошибки `NOT_MEMBER`, `CHAT_FULL` и invalid payload — ожидаемые бизнес-отказы и считаются отдельно от системных 5xx. Перцентили измеряются histogram, а не только средним.

### 8.2. Алерты

| Алерт | Порог | Severity | Реакция |
|---|---|---|---|
| Рост системных ошибок отправки | 5xx/timeout >1% за 5 минут при трафике >100 RPS | Critical | проверить последний релиз, DynamoDB throttling, auth/Chat dependencies; при регрессии rollback |
| Задержка сохранения сообщения | p99 >800 ms в течение 5 минут | Critical | посмотреть DDB latency/throttle и latency проверки membership; ограничить retry storm |
| Перегрузка WebSocket Gateway | активные соединения >85% проектной ёмкости или connect failure >2% за 5 минут | Warning/Critical | добавить gateway nodes, проверить reconnect storm и балансировку |
| Растёт Kafka delivery lag | lag >60 секунд и растёт 5 минут | Critical | увеличить Delivery Workers; проверить недоступность Presence/Chat и DLT |
| DynamoDB throttling | >0,5% операций за 5 минут | Critical | определить горячую partition key, проверить лимиты и per-chat rate limit |
| Медиа не загружается | upload success <97% за 10 минут | Warning | проверить presigned URL, IAM/KMS, S3/CloudFront; вернуть клиенту возможность повторить загрузку |
| DR-реплика отстаёт | межрегиональный lag >60 секунд в течение 5 минут | Warning; Critical >5 минут | SRE/DBA проверяют канал, оценивают актуальный RPO и временно запрещают рискованное переключение |

Алерты имеют назначенного владельца и runbook. Для одного инцидента объединяются связанные симптомные уведомления, чтобы не создавать alert storm.

## 8.3. Логи и трейсы

- Структурированные JSON-логи: `timestamp`, `service`, `severity`, `trace_id`, `request_id`, `user_id_hash`, `chat_id`, `message_id`, `clientMessageId`, причина отказа.
- Не логировать message body, пароль, JWT, refresh token или полный push token.
- Distributed tracing через OpenTelemetry: `WSS receive → Message Service → DynamoDB write → Stream Relay → Kafka → Delivery Worker → recipient Gateway`.
- Для событий Kafka `traceparent` и `eventId` передаются в headers. Повторный event сохраняет тот же `eventId`, чтобы можно было найти причину задержки/дубликата.
- 100% traces с ошибками; базовый sampling для успешного высокочастотного realtime пути 5–10%, отдельно сохранять все traces send failures и p99 медленнее SLO.

## 9. Тестирование

### 9.1. План нагрузочного тестирования

| Сценарий | Нагрузка | Длительность | Критерии успеха |
|---|---|---|---|
| Smoke | 100 сообщений/с, 20k соединений | 10 мин | API/WSS подключается, метрики/логи/трейсы есть |
| Steady baseline | 250 отправок/с, 600 доставок/с | 30 мин | p95 сохранения ≤300 ms; 5xx <0,5%; нет потерянных подтверждённых сообщений |
| Target peak | 1 000 отправок/с, 2 400 доставок/с, 250k соединений | 60 мин | p99 сохранения ≤800 ms, p95 online delivery ≤1,5 s, Kafka lag стабилен |
| Headroom | 1 300 отправок/с, 3 000 доставок/с, 320k соединений | 30 мин | нет cascading failures; ошибки <1%; очередь после теста быстро возвращается к baseline |
| Hot group | высокая активность в одной группе из 300 участников | 15 мин | нет потери порядка в рамках чата, over-limit ограничивается rate limit, глобальные чаты не деградируют |
| Spike/reconnect | внезапно reconnect 30% WSS clients за 1 минуту | 10 мин | нет массового 5xx; rate-limit/backoff предотвращает thundering herd |
| Soak | 60% peak | 8 часов | нет роста памяти/соединений, consumer lag и диски стабильны |

Сценарии используют смесь личных и групповых чатов; 3% сообщений с медиа и 2,4 получателя в среднем. Проверяются latency p95/p99, success ratio, DDB throttling, active sockets, consumer lag, дубли и gap в истории.

### 9.2. Chaos Engineering — три эксперимента

### Эксперимент 1: потеря одного Realtime Gateway

- **Steady state:** 100 сообщений/с, 30k соединений в тестовом окружении; success ratio ≥99,5%.
- **Гипотеза:** балансировщик исключит узел, клиенты переподключатся к другим узлам, а принятые сообщения останутся сохранены в DynamoDB.
- **Blast radius:** одна нода, максимум 10% тестовых подключений.
- **Метод:** принудительно завершить процесс одного Gateway.
- **Наблюдать:** connect failures, reconnect rate, p99 сохранения, дубли/gap в истории.
- **Rollback/abort:** остановить эксперимент, если 5xx >3% две минуты или тестовая потеря сохранённых сообщений >0.
- **Результат:** измерить время восстановления соединений и корректность history sync.

### Эксперимент 2: увеличение latency/ошибок Message Store

- **Steady state:** 250 отправок/с, p99 persist ≤800 ms.
- **Гипотеза:** bounded retry и timeout не создадут retry storm; Gateway не подтвердит сообщение до успешного commit.
- **Blast radius:** staging или 5% тестового трафика.
- **Метод:** fault injection — добавить 300–500 ms задержки и кратковременные throttling ответы для DDB.
- **Наблюдать:** persist latency, 5xx/timeout, повторные `clientMessageId`, очередь отправки клиента.
- **Rollback/abort:** отменить инъекцию, если ошибка отправки >2% 3 минуты или p99 >2 секунды 2 минуты.
- **Результат:** проверить, что retry идемпотентен и ack выдаётся только после сохранения.

### Эксперимент 3: остановка одного Kafka broker / замедление consumer

- **Steady state:** fan-out 600 событий/с, consumer lag <10 секунд.
- **Гипотеза:** RF=3 и `min.insync.replicas=2` позволяют пережить один broker failure; после восстановления workers догонят очередь без потери accepted-сообщений.
- **Blast radius:** один broker или одна consumer replica в staging.
- **Метод:** остановить один брокер, затем отдельно уменьшить число Delivery Workers.
- **Наблюдать:** ISR, producer errors, lag, DLT, delivery latency, дубли у получателя.
- **Rollback/abort:** немедленно прекратить, если потерян quorum или lag >5 минут.
- **Результат:** проверить репликацию, повторное чтение, дедупликацию и масштабирование consumer group.
