# ДЗ1 — Анализ референсной архитектуры: облачное хранилище Dropbox

## 0. Контекст системы

### Что делает система

Облачное хранилище Dropbox позволяет пользователю загружать, скачивать, изменять, удалять и делиться файлами, а также синхронизировать их между несколькими устройствами. На архитектурном уровне система должна одновременно обеспечивать масштабируемое хранение данных, быстрый доступ, версионирование, дедупликацию, безопасный шаринг и отказоустойчивость.

Ключевой принцип - содержимое файлов и метаданные обслуживаются разными слоями.

### Основные пользователи / акторы

1. **Авторизованный пользователь** — загружает и скачивает файлы, изменяет их, работает с версиями и синхронизирует их между устройствами.
2. **Получатель общего доступа** — читает или редактирует файл, если владелец предоставил соответствующие права.
3. **Устройство пользователя** — desktop/mobile/web client, которое инициирует загрузки, скачивания и изменения и получает уведомления о новых версиях.
4. **Асинхронные внутренние обработчики** — thumbnail generator, antivirus, search indexer и другие потребители событий. Они не являются пользователями, но участвуют в обработке данных.

### Ключевые сценарии использования

Для анализа выделю 5 основных сценариев:

1. Загрузка нового файла.
2. Скачивание файла.
3. Изменение большого файла и синхронизация только изменившихся блоков.
4. Синхронизация изменения с другими устройствами и обработка конфликта.
5. Предоставление / отзыв доступа к файлу и доставка файла через CDN.

### Масштаб

В занятии "Референс: как устроено облачное хранилище" облачное хранилище рассматривается как система масштаба **500M+ пользователей**, и как система, принимающая **500 млн файлов в день**, со средний размером файла **2 MB**, то есть примерно **1 PB новых данных в сутки**. Это порядок масштаба, при котором обычная файловая система или один storage-сервер уже не подходят.

Поэтому далее предполагается:

- пользователей — сотни миллионов;
- объём данных — петабайты и выше;
- поток загрузки — порядка 500 млн файлов/сутки;
- архитектура должна горизонтально масштабироваться по нескольким слоям.

# 1. Компоненты

**Основные сервисы и их ответственности (5-10 компонентов)** архитектуры Dropbox.

1. **Client (клиентское приложение, Stateful)**
    1. Загружает файлы
    2. скачивает файлы
    3. обнаруживает локальные изменения
    4. хранит локальный кэш
    5. получает уведомления
2.  **API Service/Gateway (stateless-сервис)**
   1. Принимает клиентские запросы
   2. маршрутизирует запросы к нужным внутренним компонентам
3. **Metadata Service + sharded MySQL** (Service — stateless, DB — stateful)
   1. хранит структуру файлов, версии и ссылки на блоки
   2. определяет, где лежит содержимое
4. **Magic Pocket / Block Storage** (распределённое хранилище, Stateful)
   1. хранит содержимое файлов в блоках 4 MB и SHA-256 как адрес блока
5. **Sync Engine (stateful/координирующий сервис)** 
   1. Вычисляет дельту изменений
   2. отслеживает версии, перемещения и конфликты
   3. организует синхронизацию между устройствами
   4. Состояние хранится в БД/журнале; worker-часть масштабируется горизонтально |
6. **Event Bus** (очередь, Stateful)
   1. Передаёт события асинхронным подписчикам
7. **Notification Service** (stateless-сервис)
   1. Доставляет пользователям уведомления о появлении или изменении файлов
8. **Search Index / Search Indexer** (индекс + consumer)
   1. Поддерживает индекс имён и метаданных файлов, чтобы поиск не нагружал основную metadata DB
9. **CDN + Signed URLs** (CDN / edge cache, stateful cache)
   1. Кэширует часто читаемые файлы ближе к пользователю и отдаёт их по временным подписанным ссылкам
10. **Auth / ACL / Audit** (сервис безопасности. Сервис — stateless, данные прав — persistent state)
   1. Проверяет аутентификацию и права доступа
   2. поддерживает аудит обращений к файлам

Ни один компонент не отвечает сразу за всё:

- storage хранит байты, но не решает задачи синхронизации;
- metadata хранит состояние файлов, но не передаёт пользовательский контент;
- sync engine отвечает за изменения и конфликты;
- event bus выносит вторичные операции из синхронного пути;
- CDN отвечает за быстрый read, но не является источником истины.

metadata layer отвечает за состояние файлов и ссылки на блоки, storage layer отвечает за содержимое, а sync/event/CDN слои решают задачи вокруг основного хранения.

# 2. Ключевые потоки данных

## Сценарий 1. Пользователь загружает новый файл

### Последовательность

1. Пользователь выбирает файл в клиентском приложении.
2. Client отправляет запрос в API Service.
3. API Service проверяет авторизацию и права.
4. Запускается путь записи файла через Sync Engine / storage layer.
5. Файл разбивается на блоки по 4 MB.
6. Блоки записываются в Magic Pocket.
7. Metadata Service записывает в sharded MySQL информацию о версии файла и ссылках на блоки.
8. После успешной записи публикуется `file.uploaded`.
9. Event Bus доставляет событие асинхронным потребителям.
10. Search Indexer обновляет индекс; Notification Service уведомляет другие устройства; аналогично могут работать thumbnail generator и antivirus.

**Синхронная часть:** запись блоков + фиксация метаданных.

**Асинхронная часть:** обработчики событий после успешного сохранения.

**Что происходит при сбое:**

- если временно недоступен Event Bus, сам файл не должен считаться потерянным
- события должны иметь retry, поэтому вторичные функции могут задержаться;
- пользователь может увидеть файл раньше, чем будут готовы thumbnail или поисковый индекс.

## Сценарий 2. Пользователь скачивает файл

### Последовательность

1. Client запрашивает файл у API Service.
2. Auth / ACL проверяет право чтения.
3. Metadata Service определяет актуальную версию и ссылки на блоки.
4. API формирует короткоживущий Signed URL.
5. Client обращается к CDN.
6. Если нужные данные есть в кэшк, CDN сразу отдаёт файл.
7. При файл отсутствует в CDN-кэш, то получает содержимое из Magic Pocket и затем отдаёт его пользователю.

**Синхронная часть:** авторизация, получение метаданных, выдача signed URL.

**Основной поток данных:** Client → CDN → Storage.

**Что происходит при сбое:**

- при временном отсутствии CDN-кэша пользователь получает дополнительную задержку, но данные можно прочитать из Object Storage;
- при недоступности Object Storage чтение завершается ошибкой;
- после истечения TTL signed URL запрос должен быть отклонён.

## Сценарий 3. Пользователь изменил 100 MB файл на 1 байт

Вместо повторной передачи всего файла система работает с **block-level delta sync**, где передаются только изменившиеся блоки 4 MB.:

1. Client обнаруживает локальное изменение.
2. Sync Engine сравнивает новую версию с предыдущей.
3. Определяется изменившийся блок.
4. Передаётся только изменившийся блок.
5. Новый блок сохраняется в Magic Pocket.
6. Metadata Service фиксирует новую версию.
7. Публикуется `file.changed`.
8. Notification Service сообщает другим устройствам о новой версии.

**Главный trade-off:** уменьшается сетевой трафик и ускоряется синхронизация, но Sync Engine становится значительно сложнее.

## Сценарий 4. Изменение приходит одновременно с двух устройств

Проблема: ноутбук и телефон могли быть офлайн, и оба изменили один файл.

### Последовательность

1. Каждое устройство сохраняет локальную версию.
2. После восстановления соединения версии приходят на сервер.
3. Sync Engine сравнивает версии и историю изменений.
4. Если изменения совместимы, синхронизация может продолжиться.
5. Если автоматическое разрешение невозможно, применяется политика conflict resolution: например, создаётся conflict copy или выбирается одна из версий по заданному правилу.
6. Итоговая версия фиксируется в metadata layer.
7. Другие устройства получают событие изменения.

**Что происходит при сбое:**

- если одно устройство временно недоступно, его версия просто появится позже;
- если два изменения конфликтуют, нельзя молча считать, что данные корректно объединились — используется явная стратегия разрешения конфликта;
- если event bus недоступен, уведомление может задержаться, но уже сохранённая версия не должна исчезнуть.

## Сценарий 5. Пользователь делится файлом и затем отзывает доступ

1. Владелец инициирует изменение Access Control List (ACL).
2. Auth / ACL проверяет, имеет ли владелец право делиться файлом.
3. Изменение прав фиксируется в persistent state.
4. Публикуется `file.shared`.
5. Notification Service сообщает получателю о новом доступе.
6. При скачивании получатель снова проходит проверку ACL.
7. При отзыве доступа новые запросы должны перестать получать разрешённый signed URL.
8. Уже скачанная копия пользователя, конечно, физически не может быть удалена из его устройства.

**Синхронно:** изменение ACL и проверка прав.

**Асинхронно:** уведомление пользователя и аудит.

# 4. Проблемы и решения

1. Петабайты данных. Один storage-сервер и обычная FS стали бы узким местом. Решение - Distributed Block Storage / Magic Pocket, но сложнее эксплуатация и rebalancing
2. Большой объём метаданных.  Одна БД стала бы bottleneck. Решение - Sharded MySQL, но сложнее маршрутизация и миграция данных
3. Передача всего файла при маленьком изменении. Решение - Block-level sync, но много лишнего трафика и медленная синхронизация. Сложнее Sync Engine
4. Повторяющиеся блоки. Одинаковые данные хранились бы многократно. Решение - Content-addressable storage по SHA-256
5. Отказ storage-ноды. Решение - Replication / Erasure Coding | Часть данных стала бы недоступной или потерянной | Репликация дороже; EC сложнее читать/восстанавливать |
6. Медленный глобальный read. Каждый download шёл бы в origin. Решение - CDN, но Cache может устаревать, нужна стратегия TTL/invalidation
7. Проюлема доступа по постоянной ссылке. Ссылка могла бы действовать слишком долго. Решение - Signed URL с коротким TTL, но пользователю иногда нужно повторно получать ссылку

### 4.1. Масштабирование

**1. Stateless services.**  
API Service, Notification Service и обработчики событий можно горизонтально масштабировать добавлением экземпляров.

**2. CDN.**  
Для глобального чтения добавляются edge-точки присутствия, а нагрузка на origin уменьшается за счёт cache hit.

### 4.2. Надёжность

- **репликация** — для горячих данных;
- **Erasure Coding** — для экономичного хранения холодных данных;
- **Event Bus как буфер** — чтобы временный сбой consumer не ломал основной upload;
- **immutable blocks** — старая версия не перезаписывается на месте;
- **versioning** — позволяет восстановить предыдущую версию;
- **retry асинхронных обработчиков** — позволяет догнать отложенные события.

# 5. Ключевые trade-offs

### Block-level sync

Передача только изменившихся блоков экономит трафик и ускоряет синхронизацию, но требует сложного sync engine.

### Replication - Erasure Coding

Репликация быстрее и проще для чтения, но требует больше места. Erasure Coding экономит storage, но требует сбора нескольких частей и декодирования при восстановлении, поэтому повышает сложность и latency.

### Strong consistency - Eventual consistency

Для критичных metadata-операций нужна более строгая консистентность. Для вторичных задач — поиска, thumbnail и уведомлений — допустима eventual consistency, потому что задержка в несколько секунд не означает потерю файла.

### CDN - актуальность данных

CDN уменьшает latency и нагрузку на Object Storage, но создаёт проблему устаревшего cache. Поэтому используются TTL и signed URLs.
